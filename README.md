## Про проєкт

**HromadaAID** створюється для працівників органів місцевого самоврядування, які займаються призначенням, обліком і виплатою матеріальної допомоги населенню.

Мета системи – зменшити обсяг ручної роботи з таблицями, спростити підготовку платіжних документів та забезпечити послідовний облік рішень, отримувачів і виплат.

## Можливості

- **Реєстри:** облік отримувачів, рішень, призначень допомоги та банківських реквізитів.
- **Призначення й виплати:** робота з матеріальними допомогами та пов’язаними даними.
- **Платіжні документи:** формування Excel-відомостей за затвердженими шаблонами.
- **Планування та звітність:** річне планування й аналіз показників допомоги.
- **Розмежування доступу:** облікові записи, ролі та права користувачів.
- **Адміністрування:** налаштування сервера, діагностика, резервне копіювання й відновлення.
- **Автоматичні оновлення:** Client і Server Manager оновлюються через Stable GitHub Releases та універсальний Setup; API Server – через перевірений ZIP у Server Manager.

## Як влаштована система

HromadaAID складається з трьох основних компонентів:

| Компонент | Призначення |
| --- | --- |
| **HromadaAID Client** | Робочий застосунок для працівників: реєстри, документи, планування та звіти. |
| **HromadaAID API Server** | Централізована обробка даних, автентифікація та зберігання SQLite. |
| **HromadaAID Server Manager** | Налаштування й обслуговування сервера, резервні копії, оновлення та відновлення. |

```text
HromadaAID Client ──► API Server ──► SQLite
                           ▲
                           │
                  Server Manager
```

Робоча база даних зберігається **лише на сервері**. Один Fastify API Server з одним IPv4 HTTP listener `0.0.0.0:4310` обслуговує Client через loopback, LAN і Tailscale. Порт фіксований, внутрішнього TLS немає. LAN HTTP не шифрує запити; Tailscale забезпечує шифрований тунель між вузлами. Автентифікація та розмежування доступу працюють для всіх підключень.

Адресу `http://<IPv4-або-DNS-ім’я>:4310` вводять у Client вручну; вона зберігається між запусками. Автоматичного пошуку або перемикання серверів немає. Server Manager дозволяє вручну задати й зберегти Loopback/LAN/Tailscale на основному екрані та копіювати їх кнопкою. Автоматичного визначення мережевих адрес немає; ці налаштування не змінюють адресу Client чи мережу Windows. Tailscale та Windows Firewall налаштовуються окремо: HromadaAID не встановлює Tailscale й не створює firewall rules. Сервер запускається без Tailscale, інтернету чи конкретного LAN-адаптера.

## Встановлення

Для Windows передбачений **єдиний інсталятор** із вибором компонентів:

| Режим | Що встановлюється |
| --- | --- |
| **Client** | Лише робочий застосунок. |
| **Server** | API Server і Server Manager. |
| **Client + Server** | Усі компоненти на одному комп’ютері. |

1. Відкрийте розділ [Releases](https://github.com/Anatol1ch/HromadaAID/releases).
2. Завантажте універсальний Windows Setup потрібної версії.
3. Запустіть інсталятор і виберіть компоненти.
4. Для серверної інсталяції виконайте початкове налаштування в Server Manager.
5. На робочих місцях вкажіть адресу сервера у Client та увійдіть під своїм обліковим записом.

Для серверної конфігурації використовується лише `configVersion: 3`: `programDirectory`, `databasePath`, `backupDirectory`. Старі версії або транспортні поля викликають помилку без автоматичного скидання файлів чи даних. Майстер Manager має три кроки: каталоги, адміністратор, підсумок. Деталі — у [політиці транспорту](server/TRANSPORT.md).

> **Важливо:** для формування Excel-документів використовується Microsoft Excel через Windows COM. Мережева конфігурація та доступність сервера мають бути налаштовані відповідно до середовища встановлення.

## Оновлення компонентів

Система використовує **стабільні релізи GitHub**. Client і Server Manager перевіряють наявність нової версії під час запуску, періодично під час роботи та за запитом користувача. Після підтвердження нового Stable-релізу оновлення відповідного застосунку є обов’язковим.

- **Client:** завантажує перевірений Setup та оновлює лише клієнтський компонент.
- **Server Manager:** спочатку оновлює власний компонент через Setup.
- **API Server:** адміністратор підтверджує оновлення серверного ZIP у Server Manager; застосовуються перевірки цілісності, сумісності, стану служби та API.

Перевірка SHA-256 захищає цілісність завантажених файлів, але не замінює цифровий підпис видавця.
