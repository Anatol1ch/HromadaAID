# Інструкції для Codex

## Початок роботи

1. Прочитай `docs/HANDOFF.md`, потім лише потрібні частини `docs/PROJECT.md`,
   `docs/ARCHITECTURE.md`, `docs/DECISIONS.md` та `docs/ROADMAP.md`.
2. Перевір фактичні гілку, HEAD і `git status --short`. Очікувана робоча гілка —
   `feature/client-server`; не роби checkout/reset без завдання користувача.
3. Зберігай сторонні незакомічені зміни. Не використовуй старі артефакти як доказ
   актуальної збірки. Фактичний код має пріоритет над застарілими описами.

## Межі роботи

- Внось мінімальні зміни відповідно до завдання. Спочатку цільово оглянь пов'язані
  файли, імпорти, конфігурації й тести; не проводь повний аудит без потреби.
- Використовуй наявні механізми та дизайн-систему. Не створюй паралельні backup,
  restore, update або recovery engines.
- Без прямої вказівки не запускай packaging, не створюй дистрибутиви, tag,
  GitHub Release і не виконуй push. Коміт створюй, коли це вимагає завдання.
- Не змінюй версію, залежності, API-контракти, SQLite schema, RBAC, автентифікацію,
  TLS, ACL, DPAPI, шифрування чи формат архівів без необхідності в межах завдання.
- Не змінюй реальну Windows Service, робочі SQLite, ключі, конфігурації або копії
  на машині розробника. Руйнівні сценарії — лише окремі тестові дані/VM за явним
  дозволом. Не очищуй невизначені транзакційні артефакти.
- Не записуй паролі, токени, аварійні ключі, персональні чи банківські дані в логи,
  документацію, frontend persistent storage або Git. Локальні `reference/*.xlsx`
  можуть містити реальні дані; не додавай їх до коміту.

## Перевірки

- Використовуй risk-based перевірки: відповідний TypeScript і цільові наявні тести.
  Не запускай повний suite, якщо цільових перевірок достатньо.
- Не додавай тести простих візуальних деталей, snapshot чи GUI smoke без потреби.
  Візуальну якість, DPI, відступи й прості GUI-сценарії залишай користувачу у VM.
- Для recovery перевіряй передумови, збереження копій/журналів, відмову за
  неоднозначного стану та блокування паралельних операцій. Mock SCM не доводить
  працездатності реальної служби або її ACL.
- Перед завершенням перевір diff, `git diff --check` і Git-стан. Не пакуй застосунки
  лише для перевірки документації або невеликого UI-виправлення.
- Команди `build`, `manager:build`, `server:build` компілюють код; `windows:package`,
  `windows:installer`, `*:portable`, `windows:deployment-packages` створюють пакети
  або викликають пакування. Перевіряй `package.json` перед запуском.

## Контекст між чатами

- `PROJECT` описує продукт; `ARCHITECTURE` — реалізацію; `DECISIONS` — незмінні
  домовленості; `ROADMAP` — статус етапів; `HANDOFF` — поточний стан і наступний крок.
- За істотних змін оновлюй відповідний документ без дублювання описів. У HANDOFF
  розрізняй реалізоване, автоматично перевірене та те, що ще потребує VM.
- Завершуй завдання стислим звітом українською: результат, перевірки, обмеження,
  коміт (якщо створено) та стан робочого дерева.
