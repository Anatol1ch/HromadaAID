# Stage 9.2 — Windows 10 x64 VM manual acceptance

**Статус: НЕ ВИКОНАНО. Stage 9.2 очікує приймання.** Цей документ є чеклістом,
а не звітом про PASS. Автоматичні перевірки описані в [HANDOFF.md](HANDOFF.md).
Транспорт і конфігурація — у [TRANSPORT.md](../server/TRANSPORT.md).

## Передумови й запис середовища

- Чиста Windows 10 x64 VM і snapshot перед встановленням. Кожен режим A1–A3
  перевіряти після повернення до чистого snapshot або в окремій чистій VM.
- Свіжий Universal Setup, зібраний із погодженого стану Stage 9.2. Зафіксувати
  версії Client/API/Manager, Git checkpoint і SHA-256 пакета, наданий разом із ним.
  Поточний опублікований 0.1.6 не є тестовим кандидатом. Packaging у Prompt 4
  не виконувався; для підготовки пакетів потрібне окреме завдання.
- Права адміністратора Windows для Setup і керування службою. Усі дані — синтетичні.
  Зберегти аварійний ключ через GUI окремо; не вставляти його, паролі чи токени в протокол.
- Для LAN потрібен другий ПК/VM із Client, доступний IPv4 маршрут до сервера та
  дозволені вхідні TCP-з'єднання на 4310 у відповідному профілі Windows Firewall.
  Вибрати підходящий режим мережі VM (наприклад, bridge або маршрутизована мережа).
  Одна ізольована VM не доводить доступ із LAN.
- Для Tailscale потрібні два вузли зі встановленим і налаштованим зовні Tailscale,
  доступом до потрібного tailnet та політикою, яка дозволяє TCP 4310. Для DNS-тесту
  потрібен LAN DNS або MagicDNS, що повертає доступну IPv4 сервера.
- Для одночасного C9 потрібні клієнтські сеанси через loopback, LAN і Tailscale
  до одного сервера. Доступність кожного маршруту має бути підтверджена окремо.
- Для E2/E4 потрібні погоджені тестові пакети R1 → R2 (R2 новіший за SemVer),
  **обидва з актуальним HTTP/config v3**, та Manager узгодженої версії. Для E3 —
  підготовлена пошкоджена копія ZIP, для E4 — тестовий пакет/fixture з контрольованою
  помилкою запуску після активації. Самостійно не підміняти файли/хеші пакета.
  Якщо таких матеріалів немає, ці перевірки позначити «БЛОКОВАНО».

## A. Чисте встановлення

- [ ] **A1 — Client-only.** У Setup вибрати «Клієнт». Очікується Client без нової
  HromadaAIDApi і Server Manager; для роботи вручну задається адреса окремого сервера.
- [ ] **A2 — Server-only.** Із чистого snapshot вибрати «Сервер». Очікуються API +
  Manager без Client. Завершити початковий майстер; раніше нього дані не ініціалізувати.
- [ ] **A3 — Server + Client.** Із чистого snapshot вибрати повний комплект.
  Очікуються обидва застосунки й одна HromadaAIDApi; Client підключається до loopback.
- [ ] **A4 — UAC.** На окремій спробі скасувати запит підвищення прав: успіх не
  заявляється. Повторити зі згодою; зафіксувати результат. Наявні дані не скидаються.
- [ ] **A5 — Початкове налаштування.** Через Manager пройти лише «Каталоги →
  Адміністратор → Підсумок», зберегти аварійний ключ через GUI й підтвердити.
  Немає вибору host/port/режиму/TLS. На завершенні — стани служби/API та версія,
  без адрес; після «Готово» адреси доступні в огляді Manager.
- [ ] **A6 — Файли й служба.** У Провіднику перевірити вибрані Data/Backups та
  Logs. Відкрити server.json у Блокноті без збереження: лише configVersion=3,
  programDirectory, databasePath, backupDirectory. У «Службах» відкрити властивості
  HromadaAIDApi: LocalService і автоматичний відкладений запуск. Повторний запуск
  застосунків не створює нову порожню базу.

## B. Робота сервера

- [ ] **B1 — Запуск без Tailscale/інтернету.** На серверній VM не встановлювати або
  вимкнути Tailscale, тимчасово відключити зовнішню мережу. Через Manager запустити
  API; очікуються Running і локальний health. GitHub update-check може бути недоступним.
- [ ] **B2 — Зупинка.** Через Manager зупинити сервер і підтвердити дію.
  «Служби» показують Stopped, локальний API недоступний; Client зберігає адресу.
- [ ] **B3 — Перезапуск.** Запустити/перезапустити через Manager. Зупинка й запуск
  відображаються як процес; успіх — після Running та свіжого health, а не лише SCM.
- [ ] **B4 — Перезапуск Windows.** Перезапустити VM, дочекатися відкладеного
  автозапуску служби. Manager і Client відкриваються окремо; API та тестові дані доступні.
- [ ] **B5 — Локальний health.** У браузері серверної VM відкрити
  `http://127.0.0.1:4310/health`. Очікується JSON зі status=ok,
  service=hromada-aid-api, apiContractVersion=1; перевірка не вимагає входу.
- [ ] **B6 — Один listener.** У «Моніторі ресурсів → Мережа → Порти прослуховування»
  перевірити один IPv4 listener API на 0.0.0.0:4310, без додаткового IPv6 listener.
  WinSW запускає один серверний Node-процес. Кілька адрес у Fastify Logs самі по
  собі не означають кілька listener-ів.
- [ ] **B7 — Поява інтерфейсів.** З працюючим API ввімкнути Tailscale; повторити C3
  без перезапуску служби. Якщо можливо, змінити LAN IPv4 через GUI тестової мережі
  та повторити C2 з новою адресою: API не потребує повторного bind. Client не
  вгадує нову адресу — її змінюють вручну або використовують оновлений DNS.

## C. Підключення Client

- [ ] **C1 — Loopback.** На серверному ПК вручну задати `http://127.0.0.1:4310`,
  перевірити, зберегти, увійти. 0.0.0.0 не є адресою для Client.
- [ ] **C2 — LAN.** На другому ПК/VM задати `http://<LAN-IPv4>:4310`.
  Health і вхід працюють за наявності передумов; LAN HTTP не шифрується.
- [ ] **C3 — Tailscale.** На іншому вузлі tailnet задати `http://<Tailscale-IPv4>:4310`.
  За можливості перевірити з іншої мережі. Дані й користувачі належать тому самому API.
- [ ] **C4 — DNS.** Задати `http://<LAN-DNS-або-MagicDNS-ім’я>:4310`, яке резолвиться
  у доступну IPv4. Перевірити підключення, вхід і відкриття даних.
- [ ] **C5 — Збереження адреси.** Повністю закрити й відкрити Client. Адреса
  відновлюється, автоматичного переходу на інший сервер немає; новий запуск
  потребує нового входу, бо сесія не зберігається як постійний токен.
- [ ] **C6 — Втрата й відновлення зв'язку.** Перервати обраний маршрут або зупинити
  API через Manager. Після повернення маршруту повторити підключення штатною дією.
  Адреса не видаляється; використовується той самий сервер, сесія обробляється штатно.
- [ ] **C7 — Ручна зміна адреси.** Через наявні налаштування Client змінити маршрут
  до того самого сервера (або до другого тестового сервера, якщо він є).
  Перед збереженням виконується перевірка; попередня сесія завершується, потрібен вхід.
  Непрацездатна нова адреса не підміняє збережену. Неправильний порт і HTTPS відхиляються.
- [ ] **C8 — Доступ.** Увійти під тестовими адміністратором і обмеженим користувачем.
  Доступні лише дозволені дії; вихід/завершення сесії потребують нового входу.
  Мережевий Client не отримує права керування локальною Windows Service.
- [ ] **C9 — Єдині дані.** Одночасно підключити сеанси через loopback/LAN/Tailscale.
  Створити синтетичний запис у дозволеному довіднику, оновити списки в інших
  сеансах: усі бачать одну серверну базу без додаткових серверів або копій SQLite.

## D. Server Manager

- [ ] **D1 — Стани.** Порівняти Manager зі «Службами» й B5. SCM і API мають окремі
  стани. Під час переходів або помилки API статус Running не видається за готовність API.
- [ ] **D2 — Loopback/LAN.** В огляді є 127.0.0.1:4310 та доступні фізичні LAN IPv4.
  За наявності Ethernet і Wi-Fi перевірити обидва; 0.0.0.0 не пропонується для Client.
- [ ] **D3 — Без Tailscale.** Немає вигаданої Tailscale-адреси або вимоги його
  встановити; огляд і керування службою працюють.
- [ ] **D4 — З Tailscale.** Оновити перевірку середовища. Адреса з'являється лише
  якщо адаптер визначено за метаданими. Непідтверджений адаптер не класифікується
  лише за CGNAT IP; його адресу можна ввести в Client вручну, як у C3.
- [ ] **D5 — Копіювання.** Для кожного показаного типу адрес скопіювати URL і
  вставити в Блокнот/налаштування Client. Очікується саме HTTP URL з портом 4310.
- [ ] **D6 — Межі UI.** Адреси показуються лише на основному екрані. У конфігурації
  та майстрі немає вибору мережевого режиму, адаптера, host, port чи TLS; на
  завершальному екрані майстра немає списку адрес. HromadaAID не додає firewall rules.

## E. Оновлення та відновлення

Перед кожним негативним сценарієм — окремий snapshot і тестова резервна копія.
Пакети в цьому розділі мають лише актуальний transport і config v3.

- [ ] **E1 — Резервна копія.** Через Manager увійти з потрібним дозволом,
  створити, перевірити й експортувати архів. Обмежений користувач не отримує ці права.
- [ ] **E2 — Оновлення R1 → R2.** Через Manager вибрати погоджений новіший Server ZIP,
  перевірити preview та підтвердити. Успіх — лише після правильної версії пакета,
  Running та локального health. Наявні записи, користувачі, шляхи й архіви збережені.
- [ ] **E3 — Integrity.** Вибрати підготовлену пошкоджену копію ZIP. Вона відхиляється
  до активації; поточний сервер і SQLite не підміняються. Для зовнішніх завантажень
  залишається HTTPS; не встановлювати старий Stable 0.1.6 як кандидата Stage 9.2.
- [ ] **E4 — Відмова й recovery/rollback.** Застосувати погоджений fixture з помилкою
  запуску після активації. Manager не показує успіх. Скористатися наявним recovery,
  якщо він пропонується: повертається перевірений попередній пакет актуального
  транспорту лише за сумісної схеми. За неоднозначного стану пакети/журнал збережені,
  дія заблокована з причиною. Не видаляти артефакти вручну, щоб «розблокувати» повтор.
- [ ] **E5 — Restore через GUI.** Зробити копію тестових даних, додати контрольну зміну,
  потім явно підтвердити restore попереднього архіву в Manager. Перевірити зупинку/
  запуск служби, health, повторний вхід та очікуване повернення даних до копії.
  Страхові матеріали збережені за чинним механізмом; restore не є оновленням пакета.
- [ ] **E6 — Несумісна конфігурація.** Лише в окремому snapshot: зупинити службу,
  зберегти копію server.json і через Блокнот змінити configVersion на 999.
  Manager/запуск повідомляє про несумісність, не переписує файл і не створює іншу
  SQLite. Повернути оригінальний v3 файл вручну або відновити snapshot. Це перевірка
  відмови за невалідної схеми, а не приймання старої архітектури.
- [ ] **E7 — Оновлення 0.2.0 → 0.2.1.** Лише після ручної публікації Stable 0.2.1,
  оновити наявну VM з 0.2.0 — не видаляти її й не робити чисту інсталяцію. Перевірити
  Client і Server Manager через Stable Setup, потім API Server через Server ZIP.
  Переконатися, що `server.json`, SQLite й записи збережені, служба працює, Manager
  показує та копіює Tailscale IPv4, а Client авторизується через Tailscale. Зараз
  оновлення не запускати.
