# Stage 9.1.3 – Аудит безпеки перед публікацією

Дата аудиту: 2026-10-26

## Executive summary

**READY FOR PUBLICATION** для вихідного репозиторію за рішеннями власника: він підтвердив знеособлення трьох Client document templates і прямо дозволив публікацію власної контактної картки. За цими вказівками шаблонів не сканували повторно, картку не змінювали, Git history не переписували. Поточні локальні release artifacts потрібно перебудувати перед їх публікацією, оскільки вони створені до оновлення шаблонів.

Це висновок щодо публікації вихідного репозиторію в межах попереднього цільового аудиту, а не твердження про production readiness Stage 9.1. Ручні Windows VM і live GitHub Release перевірки лишаються окремими передумовами.

Сканування доступної Git-історії не виявило production credentials або приватних ключів. Знайдені ключі належать самопідписаним TLS test fixtures. Це результат цільового аудиту готовності до публікації, а не повний penetration test.

### Follow-up: перевірка `reference/` (2026-10-26)

`Список.xlsx`, `Зведений список.xlsx` і `ПриватБанк.xlsx` є шаблонами, які Client використовує для формування вихідних документів. Скрипти генерації заповнюють їх даними поточної бази. Власник вручну знеособив ці три файли та підтвердив їхню придатність до публікації; повторного аналізу їхніх даних не виконували. `Реєстр.xlsx`, вхідне джерело окремого імпортера, власник видалив; його не відновлювали.

Production build явно копіює три шаблони з `reference/` у Client payload; це очікуване runtime-включення, оскільки документогенератори їх читають. `.gitignore` тепер дозволяє відстежувати лише три названі шаблони та ігнорує інші елементи `reference/`. Release artifacts, зібрані до оновлення шаблонів, застарілі й потребують нової збірки перед публікацією.

Client portable ZIP не є залежністю первинного встановлення чи автоматичного оновлення: updater завантажує універсальний Setup, а release manifest містить лише Setup та Server ZIP. Client portable є окремим необов'язковим способом ручного перенесення/запуску. Manager portable каталог та його серверний runtime payload, навпаки, потрібні чинному процесу підготовки універсального Setup; Server ZIP потрібний API Server update.

## Scope

- Поточна гілка: `feature/client-server`; HEAD: `521251067e2f9c6f81559ea337402e61dfbd78e5`.
- Перевірено Git-tracked files поточного HEAD, назви файлів та вміст доступних історичних Git objects для всіх локально досяжних refs: 122 коміти, репозиторій не shallow.
- Перевірено локальні гілки й теги та віддалені refs, оголошені `origin`: доступна лише `origin/main` (`3cc90daad5ba23fd7a8ca414ac8280250d03fd18`), тегів немає. Відповідна історія `origin/main` доступна локально. Картка контакту з feature-коміту не входить до історії `origin/main`.
- Не охоплено неоголошені або видалені refs на сервері GitHub, а також refs, недоступні поточному обліковому запису.
- Перевірено `.gitignore`, конфігурацію packaging та наявні Stage 9.1.3 артефакти без повторного packaging; переглянуто склад `app.asar` для Client та Server Manager.
- У середовищі не знайдено встановлених `gitleaks`, `trufflehog`, `detect-secrets`, `git-secrets` чи `secretlint`. Замість них застосовано цільові евристичні пошуки по історичних об'єктах, списках файлів і релевантних текстових конфігураціях з ручною перевіркою redacted-збігів. Це не еквівалент сертифікованого сканера секретів.
- Вміст локальних таблиць перевірено лише структурно та за шаблонами; значення комірок не включалися у звіт. Реальність чи синтетичність записів потребує власницької перевірки.

## Findings

### F-01 – Client document templates у production payload

- **Severity:** Informational
- **Шлях:** `reference/Список.xlsx`, `reference/Зведений список.xlsx`, `reference/ПриватБанк.xlsx`.
- **Ризик:** потрібні runtime templates входять до Client payload. Власник підтвердив, що їх вручну знеособив; за його прямою вказівкою цей аудит не перевіряв їхній вміст повторно.
- **Git-статус:** ці три файли призначені для відстеження; решта `reference/` ігнорується. `Реєстр.xlsx` власник видалив і його не слід відновлювати.
- **Використання:** `Список.xlsx` і `Зведений список.xlsx` читаються `electron/statements-ipc.ts` як основа персональної та зведеної відомостей; `ПриватБанк.xlsx` — як основа платіжного XLSX. Їхній layout потрібний Excel COM генераторам. `Реєстр.xlsx` раніше читав лише `scripts/import-2026-register.py` як джерело імпорту; власник його видалив. Три шаблони призначені для Git, імпортне джерело не відстежується й packaging його не копіює.
- **Причина включення:** `electron/copy-assets.mjs` явно копіює перші три файли в `dist-electron/electron/reference`; `package.json` включає цей каталог у `app.asar`. `scripts/package-client-portable.mjs` перевіряє наявність цих трьох шаблонів. Server Manager payload їх не включає.
- **Рекомендація:** збирати Client payload із цих трьох відстежуваних шаблонів; не включати імпортні реєстри чи інші локальні документи. Перед публікацією інсталяторів оновити release artifacts.
- **Статус:** Шаблони підготовлено власником; технічні generation/packaging checks пройшли (див. HANDOFF). Stage 9.1.3 binaries не перебудовані.

### F-02 – Контактні дані адміністратора/розробника у UI feature-гілки

- **Severity:** Medium
- **Шлях і призначення:** `src/App.tsx`, модальне вікно «Допомога та підтримка» з контактною карткою адміністратора/розробника. Вона є у HEAD і в 60 доступних commit trees гілки `feature/client-server`, починаючи з `f4f4a29890a64e250ebfa07cd169c43af753ee77` і до HEAD `521251067e2f9c6f81559ea337402e61dfbd78e5`; серед комітів, що змінювали `src/App.tsx`, останній із карткою — `dbd06403f90f5d80ec52c5e93ee5bbb0233a4b3a`. Інші локальні гілки її не містять; `origin/main` також не містить.
- **Ризик:** у UI є прямі контактні реквізити власника.
- **Рекомендація:** власник прямо дозволив публікацію. Не редагувати картку та не переписувати історію через неї.
- **Статус:** Прийнято власником для публікації.

### F-03 – Приватні ключі лише у TLS test fixtures

- **Severity:** Informational
- **Шлях:** `server/test-fixtures/tls-test-key.pem`, `server/test-fixtures/tls-other-test-key.pem` (сертифікат поруч у тому ж каталозі); історія містить їх як тестові fixtures.
- **Ризик:** сканер знайшов блоки приватних ключів, але посилання у коді ведуть до TLS-тестів і тестової конфігурації. Ознак production використання або включення в пакети не знайдено. Це тестові ключі; не виявлено ознак повторного використання в production.
- **Рекомендація:** залишити тільки як тестові fixtures; ніколи не використовувати ці ключі поза тестами. Перевірено, що server packaging відхиляє PEM/ключові файли та не включає fixtures.
- **Статус:** Перевірено; не блокує публікацію за умови суто тестового використання.

### F-04 – Посилено локальні правила `.gitignore`

- **Severity:** Low
- **Шлях:** `.gitignore`.
- **Ризик:** до аудиту не ігнорувалися поширені розширення локальних приватних ключів і crash dumps; можна було випадково додати такі файли в майбутньому. Тестові PEM fixtures лишаються явними винятками.
- **Рекомендація:** зберегти додані вузькі правила та надалі перевіряти `git status` перед комітом. `.gitignore` не захищає файли, які вже відстежуються Git.
- **Статус:** Виправлено в незакоміченій зміні цього завдання.

### F-05 – Секрети в доступному коді та історії

- **Severity:** Informational
- **Шлях:** Git-історія всіх локально досяжних refs.
- **Ризик:** евристичний сканер не знайшов ознак production GitHub/API/CI credentials, JWT signing secrets, production TLS/private keys або code-signing secrets. Знайдені схожі рядки вручну класифіковано як тестові значення, приклади, перевірки форматів або UI labels. Висновок обмежений евристичним пошуком та доступним охопленням refs.
- **Рекомендація:** перед відкриттям повторити scan спеціалізованим secret scanner, якщо він доступний у CI/середовищі власника; перевірити нові refs, які планується залишити у GitHub.
- **Статус:** Перевірено в межах описаного scope; підтверджених production secrets не виявлено.

## Перевірка `.gitignore` та пакетів

- Ігноруються production `.env`-варіанти, SQLite та журнали, резервні копії, runtime logs, локальні XLSX у `reference/`, каталоги збірки й `release/`. Для приватних ключів і crash dumps додано вузькі правила; потрібні TLS test fixtures залишені явними винятками.
- `.gitignore` не знімає з відстеження наявні файли. Перевірено, що Excel-книги не є tracked.
- Stage 9.1.3 артефакти знаходяться поза Git під `release/`; їх не потрібно видаляти з індексу.
- Client `app.asar` містить три локальні reference XLSX. Server Manager `app.asar` їх не містить.
- Переглянута серверна packaging-конфігурація виключає runtime data, test/fixture каталоги та приватні ключі; серверний ZIP має integrity manifest. Ця перевірка не замінює аудит кожного майбутнього release artifact.
- У конфігурації релізів знайдено назву репозиторію, але не GitHub токен. Code signing не налаштований для локально зібраних артефактів; це окреме питання довіри до Windows-поширення, не витік секрету.

## Publication readiness

**READY FOR PUBLICATION** для source repository згідно з підтвердженнями та рішеннями власника.

Це не означає, що локальні інсталятори готові до публікації: наявні Stage 9.1.3 binaries не перебудовувалися після знеособлення шаблонів. Спершу слід завершити запитані перевірки, а нове пакування й release publication виконати окремим погодженим кроком.

## Рекомендовані дії перед зміною видимості

1. Відстежувати лише три дозволені Client templates; не додавати інші документи з `reference/`.
2. Після успішного технічного огляду за окремим погодженням перебудувати Setup і Server ZIP/manifest. Client portable не потрібен обов'язковому release workflow.
3. Зберігати Windows VM та live GitHub update сценарії як невиконані до їх фактичного проходження; READY для source visibility не є production-ready для Stage 9.1.

Власник дозволив публічний репозиторій і публікацію контактної картки. Під час поточного етапу не змінюються repository visibility, GitHub Releases, інсталяції, Windows Service чи робочі дані; push, tag і history rewrite не виконуються. Пакети не перебудовуються.
