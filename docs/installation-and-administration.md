# HromadaAID – встановлення та адміністрування

Версія документації: 1.0.1. Дата: 30.10.2026.

**Статус 1.0.1: підготовлено локально, ще не опубліковано.** Останній підтверджений опублікований Stable — 1.0.0. Нові можливості описано для майбутнього релізу 1.0.1.

Практична інструкція для працівників органів місцевого самоврядування (ОМС) із базовими навичками Windows. Вона охоплює встановлення, підключення робочих місць і обслуговування системи. Налаштування маршрутизатора, Windows Firewall і Tailscale виконуються окремо від HromadaAID.

> Усі адреси в прикладах умовні. Підставляйте адреси своєї мережі. Аварійні сценарії й модельно-залежні мережеві налаштування перевіряйте спочатку на окремому середовищі.

## Швидкий початок

Для роботи на одному комп'ютері:

1. Завантажте Universal Setup із [офіційних Releases](https://github.com/Anatol1ch/HromadaAID/releases) потрібної опублікованої версії.
2. Запустіть Setup, підтвердьте запит адміністратора Windows та виберіть «Повний комплект».
3. Відкрийте HromadaAID Server Manager. Натисніть «Налаштувати сервер» й пройдіть кроки «Каталоги», «Адміністратор», «Підсумок».
4. Збережіть аварійний ключ у захищеному місці окремо від сервера й копій. Дочекайтеся підтвердження, що служба працює, а API доступний.
5. Запустіть HromadaAID. На екрані входу відкрийте налаштування підключення, перевірте й збережіть `http://127.0.0.1:4310`.
6. Увійдіть із даними створеного адміністратора. У Manager створіть і перевірте першу резервну копію.

Для кількох ПК встановіть «Сервер» на серверному комп'ютері, «Клієнт» на робочих місцях і виконайте [налаштування LAN](#section-6). Для віддаленого ПК додатково виконайте [процедуру Tailscale](#section-8).

<a id="section-1"></a>
## 1. Загальні відомості

HromadaAID призначено для обліку отримувачів і призначень матеріальної допомоги, рішень, планування, звітності та формування документів.

| Компонент | Для чого потрібний |
| --- | --- |
| Client, у Windows – HromadaAID | Робочий інтерфейс працівника |
| API Server | Приймає запити Client, перевіряє права та працює з даними |
| Server Manager | Локальне керування сервером, копіями та оновленнями |
| SQLite | Серверна база даних у файлі; окремо встановлювати SQLite не потрібно |

Client надсилає запити серверу. Робоча база фізично зберігається тільки на сервері. Клієнти не мають окремих робочих баз і потребують зв'язку із сервером. Каталог бази не потрібно відкривати як спільну мережеву папку.

| Сценарій | Що встановити | Адреса в Client |
| --- | --- | --- |
| Один ПК | Combined: «Повний комплект» | `http://127.0.0.1:4310` |
| Сервер і кілька робочих місць | Server-only: «Сервер»; на робочих ПК Client-only: «Клієнт» | LAN IPv4 сервера |
| Віддалені робочі місця | Сервер і Client; Tailscale на обох кінцях | Tailscale IPv4 сервера |

API – мережевий інтерфейс сервера. Він використовує HTTP і фіксований TCP-порт 4310. Внутрішнього TLS немає: звичайний LAN HTTP не шифрує передані дані. Використовуйте його лише в контрольованому мережевому сегменті. Для недовірених сегментів і віддаленого доступу використовуйте зовнішній захищений тунель Tailscale; звичайне HTTP-підключення через таку мережу не захищає дані.

<a id="section-2"></a>
## 2. Підготовка до встановлення

Підтримуване середовище HromadaAID – Windows 10/11 x64. Для серверних каталогів потрібні локальні фіксовані диски NTFS із вільним місцем для програми, даних, копій і тимчасових файлів оновлення. Числові мінімальні вимоги до RAM і процесора для 1.0.1 не встановлені; не використовуйте їхні довільні оцінки як офіційні вимоги.

1. Підготуйте обліковий запис із правами адміністратора Windows для Setup, початкового налаштування, керування службою та аварійних операцій. Це окремі права від адміністратора всередині HromadaAID.
2. Для формування Excel-документів установіть Microsoft Excel у Windows на робочому ПК, де їх формуватимуть. Для сервера без цих операцій Excel не є окремою передумовою.
3. Окремо встановлювати Node.js, pnpm чи засоби розробки для штатної інсталяції не потрібно. Серверний комплект містить необхідне середовище виконання.
4. Для LAN підготуйте мережеве підключення й адресу сервера. Для Tailscale – доступ до інтернету та погоджений організацією обліковий запис. Завантаження релізів також потребує інтернету.
5. Завантажте Universal Setup потрібної опублікованої версії тільки з [офіційних Releases](https://github.com/Anatol1ch/HromadaAID/releases). Очікувана назва для 1.0.1 — HromadaAID-Setup-1.0.1.exe; до публікації цей файл недоступний у Releases. Серверний ZIP призначено для керованого оновлення; його не потрібно розпаковувати замість першого встановлення.
6. Перевірте власника репозиторію `Anatol1ch/HromadaAID`, версію та назву файла. Не використовуйте випадкові перепаковані копії. Якщо Windows показує невідомого видавця, продовжуйте лише після перевірки походження файла; не вимикайте захист Windows.
7. Якщо система вже працює, узгодьте перерву, створіть перевірену резервну копію та збережіть аварійний ключ перед змінами.

Контроль: відома роль кожного ПК, є права адміністратора, отримано правильний Setup і підготовлено окреме захищене місце для копій та ключа.

<a id="section-3"></a>
## 3. Встановлення HromadaAID

1. Запустіть Setup. UAC – запит Windows на дозвіл змін – підтвердьте лише для перевіреного інсталятора; за потреби введіть дані адміністратора Windows.
2. На початковій сторінці натисніть «Далі».
3. На сторінці «Вибір компонентів» виберіть потрібний варіант:

| Напис у Setup | Режим | Склад |
| --- | --- | --- |
| «Клієнт» | Client-only | HromadaAID Client |
| «Сервер» | Server-only | API Server і Server Manager разом |
| «Повний комплект» | Combined | Client, API Server і Server Manager |

4. Виберіть папку програмних файлів. Стандартна: `C:\Program Files\HromadaAID`. Серверні дані зберігатимуться окремо.
5. Продовжте встановлення й дочекайтеся завершення. Закрийте майстер кнопкою «Готово».
6. Перевірте меню «Пуск» і робочий стіл: мають бути ярлики HromadaAID та/або HromadaAID Server Manager відповідно до вибору.
7. У списку встановлених програм Windows перевірте запис HromadaAID. У Server-only відсутність Client є очікуваною.
8. Для сервера перейдіть до [першого налаштування](#section-4). Саме копіювання компонентів Setup ще не означає готовності нового сервера.

### Зміна складу та видалення

Для зміни складу повторно запустіть Universal Setup. За підтвердженої наявної інсталяції він показує «Обслуговування HromadaAID» і дозволяє вибрати потрібний склад. Зберігайте попередній каталог. Окремої кнопки Modify в Installed Apps не передбачено.

> Перехід із повного комплекту на «Клієнт» прибирає серверні програмні компоненти та службу. Узгодьте це з користувачами. Якщо Setup повідомляє про часткову інсталяцію чи незавершену транзакцію, припиніть зміну складу й перевірте Manager.

1. Для видалення відкрийте список установлених програм Windows, виберіть HromadaAID та дію видалення.
2. Підтвердьте запит Windows і майстра видалення.
3. Дочекайтеся результату. Програмні компоненти й належні ярлики видаляються; серверна база, конфігурація та резервні копії залишаються.
4. Не видаляйте залишені серверні каталоги вручну. Повторне встановлення поверх наявних даних не є процедурою чистої ініціалізації або відновлення.

<a id="section-4"></a>
## 4. Перше налаштування сервера

1. На серверному ПК запустіть HromadaAID Server Manager із правами адміністратора Windows.
2. У «Стан сервера» виконайте «Перевірити зараз». Для підготовленого Setup сервера натисніть «Налаштувати сервер». Для стану без встановленого сервера можлива назва «Встановити сервер»; за відсутнього пакета не обходьте діагностику.
3. У майстрі «Налаштування сервера» відкривається крок «Каталоги». Перевірте шляхи:

| Призначення | Стандартний шлях |
| --- | --- |
| Програма | `C:\Program Files\HromadaAID` |
| Серверні дані | `%ProgramData%\HromadaAID\Data` |
| Резервні копії | `%ProgramData%\HromadaAID\Backups` |

`%ProgramData%` – системна папка спільних даних Windows, зазвичай `C:\ProgramData`. Її можна відкрити, ввівши `%ProgramData%` в адресному рядку Провідника.

4. Для зміни шляху скористайтеся «Огляд» або введіть його. Використовуйте окремі каталоги на локальних NTFS-дисках; не корінь диска, мережеву папку чи каталоги, вкладені один в один. Для вже підготовленого Setup пакета зберігайте визначений каталог програми. Натисніть «Далі».
5. На кроці «Адміністратор» введіть «Ім’я користувача» (до 150 символів), «Логін» (3–80 символів), «Пароль» (8–256 символів) і «Підтвердження пароля». Збережіть облікові дані захищено. Натисніть «Далі».
6. На кроці «Підсумок» перевірте каталоги й адміністратора. Натисніть «Встановити сервер».
7. У вікні «Збережіть аварійний ключ» натисніть «Зберегти у файл», виберіть захищене місце, після успішного збереження – «Я зберіг ключ». Одного копіювання в буфер недостатньо для продовження.
8. Дочекайтеся створення конфігурації, бази та адміністратора, реєстрації/запуску Windows Service і перевірки API. Windows Service – фонова служба, яка працює без відкритого Client; її назва `HromadaAIDApi`.
9. На завершенні перевірте: Windows Service працює, API доступний, показано версію сервера. Якщо є «Встановлення виконано. Потрібна перевірка», усуньте зазначену причину та натисніть «Повторити перевірку». Не ініціалізуйте дані заново.

> Чисте встановлення не перезаписує наявну базу чи ключ. Якщо виявлено старі або неповні дані, зупиніться й залучіть технічного адміністратора.

### Аварійний ключ

Ключ дає змогу розшифрувати резервні архіви після втрати серверного ключа. Без потрібного ключа придатний зашифрований архів може бути неможливо відновити. Зберігайте файл окремо від сервера і резервних копій, з доступом лише відповідальних осіб, наприклад на захищеному носії. Не надсилайте його разом з архівом поштою чи в загальний чат. Це не пароль входу до HromadaAID. Не вставляйте ключ у команди, журнали або заявки підтримки.

<a id="section-5"></a>
## 5. Підключення Client

1. Запустіть HromadaAID. На екрані «Вхід до системи» натисніть іконку налаштувань із підказкою «Налаштувати підключення».
2. У вікні «Налаштування підключення» введіть базову HTTP-адресу сервера з портом 4310:

| Приклад | Коли використовувати |
| --- | --- |
| `http://127.0.0.1:4310` | Client і сервер на цьому самому ПК; це loopback |
| `http://192.168.1.20:4310` | Інший ПК у LAN; адреса має належати серверу |
| `http://server-name:4310` | Мережа вміє визначати IPv4 сервера за цим DNS-ім'ям |

3. Натисніть «Перевірити підключення». Після успіху натисніть «Зберегти адресу». Після редагування адреси перевірте її знову.
4. Введіть «Логін» і «Пароль», надані адміністратором HromadaAID, та натисніть «Увійти». Якщо система вимагає змінити початковий пароль, виконайте вимогу.
5. Перевірте відкриття робочого інтерфейсу й доступних вашій ролі даних.

`127.0.0.1` завжди означає поточний комп'ютер: на іншому робочому ПК ця адреса не веде до центрального сервера. `0.0.0.0` – службова адреса прослуховування, її не вводять у Client. IPv6, HTTPS і довільна зміна порту не підтримуються. Не додавайте `/health` до адреси Client. Автоматичного пошуку серверів немає.

Адреса зберігається між запусками. У разі втрати зв'язку Client показує «З’єднання із сервером втрачено» й автоматично перевіряє ту саму адресу; є кнопка «Спробувати знову». Недоступність не стирає адресу. Після завершення сеансу потрібен повторний вхід.

<a id="section-6"></a>
## 6. Робота в локальній мережі

LAN – локальна мережа установи через кабель або Wi-Fi. IPv4 – адреса пристрою, наприклад `192.168.1.20`. Сервер має залишатися увімкненим, підключеним до мережі й доступним; сон або вимкнення сервера переривають роботу всіх Client. Узгодьте режим живлення з відповідальним за ІТ.

### Адреса й перевірки

1. На сервері натисніть Win+R, введіть `cmd`, натисніть Enter та виконайте:

```text
ipconfig
ipconfig /all
```

2. У блоці активного Ethernet або Wi-Fi адаптера знайдіть IPv4, маску підмережі, Default Gateway (основний шлюз) і Physical Address (MAC, фізична адреса адаптера). Не беріть адресу відключеного адаптера чи Tailscale як LAN IPv4. Адреса `169.254.x.x` зазвичай означає проблему отримання адреси, а не готову LAN-конфігурацію.
3. На сервері в браузері відкрийте `http://127.0.0.1:4310/health`. Очікується відповідь API про справність, а не сторінка іншого застосунку чи помилка. Manager додатково перевіряє формат відповіді та сумісність.
4. На робочому ПК перевірте умовну адресу сервера:

```text
ping 192.168.1.20
```

5. У PowerShell на робочому ПК виконайте:

```powershell
Test-NetConnection 192.168.1.20 -Port 4310
```

6. `TcpTestSucceeded : True` означає доступність TCP-порту. Відкрийте `http://192.168.1.20:4310/health` у браузері робочого ПК й виконайте перевірку в Client. Лише після цього зберігайте адресу за [розділом 5](#section-5).

Успішний ping доводить лише відповідь на мережевий запит, не роботу API. Невдалий ping також можливий через заборону цих запитів. Відкритий TCP-порт не доводить сумісності API чи можливості входу. Якщо локальний health працює, а віддалений ні, перевіряйте адресу, маршрутизацію й Firewall.

### Windows Firewall

Це зовнішня процедура адміністратора Windows. HromadaAID правил не створює. У доменній мережі зміни можуть керуватися політикою організації; зверніться до відповідального адміністратора.

> Не вимикайте Firewall. Не налаштовуйте переадресацію TCP 4310 з публічного WAN/інтернету на маршрутизаторі. Дозволяйте лише потрібні робочі ПК.

1. На сервері відкрийте Win+R → `wf.msc` із правами адміністратора.
2. Виберіть правила для вхідних підключень (Inbound Rules) → створення правила (New Rule).
3. Для повного налаштування виберіть Custom. Укажіть програму серверного runtime `C:\Program Files\HromadaAID\Server\runtime\node.exe`; для іншого каталогу використайте фактичний шлях установленого сервера.
4. У Protocol and Ports виберіть TCP, локальний порт 4310; віддалений порт залиште довільним.
5. У Scope задайте віддалені IPv4 дозволених робочих місць або мінімальну погоджену підмережу. Не залишайте доступ для будь-яких віддалених адрес без потреби.
6. У Action дозвольте підключення. У Profile виберіть лише фактичний профіль контрольованої мережі: Domain або Private за політикою установи. Не змінюйте недовірену мережу на Private лише заради доступу.
7. Назвіть правило, наприклад `HromadaAID API LAN TCP 4310`, завершіть майстер. Перевірте у властивостях правило, шлях програми, порт, область і профіль.
8. Повторіть TCP- і API-перевірки з дозволеного ПК. Переконайтеся, що непогоджені пристрої доступу не отримали.

Шлях `Server\runtime\node.exe` відповідає встановленому серверному пакету й зберігається після штатного оновлення API Server у тому самому каталозі програми. На цільовій Windows перевірте фактичний шлях для нестандартного каталогу та дію правила з іншого дозволеного й недозволеного ПК. Саме створення правила не доводить мережевої доступності.

Для Tailscale створіть окреме вузьке правило з Tailscale IPv4 дозволених клієнтів, потрібною локальною адресою сервера й фактичним профілем його Tailscale-інтерфейсу. Якщо він Public, дозвіл для цього профілю має бути обмежений адресами, програмою та портом; узгодьте його з ІТ-адміністратором. Не відкривайте весь діапазон Tailscale лише для одного клієнта.

Назви Windows залежать від мови. Офіційні пояснення: [Microsoft – налаштування правил Firewall](https://learn.microsoft.com/en-us/windows/security/operating-system-security/network-security/windows-firewall/configure), [Microsoft – ризики дозволів у Firewall](https://support.microsoft.com/en-us/windows/security/firewall/risks-of-allowing-apps-through-windows-firewall).

<a id="section-7"></a>
## 7. DHCP Reservation на TP-Link

### Підготовка й вибір адреси

DHCP автоматично видає мережеві адреси пристроям на певний строк – оренду. Після її оновлення або зміни мережі адреса сервера може змінитися. DHCP Reservation закріплює адресу за MAC адаптера на маршрутизаторі. Windows продовжує автоматично отримувати адресу; ручна статична IPv4 у Windows задається на самому ПК й потребує окремого контролю шлюзу, DNS та конфліктів.

1. На сервері виконайте `ipconfig /all`. Запишіть IPv4, маску, Physical Address і Default Gateway саме активного LAN-адаптера. Ethernet і Wi-Fi мають різні MAC; резервуйте той, яким користуватиметься сервер. Для Wi-Fi зі змінною випадковою MAC узгодьте стабільний ідентифікатор із адміністратором.
2. З'ясуйте, який пристрій видає DHCP-адреси. Якщо це окремий сервер, а TP-Link лише точка доступу, резервування робиться на DHCP-сервері. Не вмикайте другий DHCP без погодження.
3. Перевірте діапазон DHCP, список оренд, резервування та відомі статичні адреси. Найпростіше закріпити поточну адресу сервера, якщо вона належить йому й дозволена моделлю маршрутизатора.
4. Для нової адреси врахуйте маску й правила DHCP конкретної моделі. За маски `255.255.255.0`, шлюзу `192.168.1.1` адреса `192.168.1.20` у тій самій підмережі, але її вільність треба підтвердити. Не використовуйте адресу шлюзу, мережі `.0`, широкомовну `.255` або зайняту/зарезервовану адресу. Це правило останніх октетів стосується саме наведеного прикладу маски.
5. Невдалий ping не доводить, що адреса вільна: пристрій може бути вимкнений або блокувати відповіді. За невідомих статичних адрес залучіть мережевого адміністратора.
6. Відкрийте у браузері фактичну адресу Default Gateway й увійдіть обліковими даними адміністратора маршрутизатора. Не використовуйте припущення про стандартний пароль і не скидайте маршрутизатор.

Наведені маршрути залежать від моделі, апаратної версії та прошивки. Звірте їх із довідником вашого пристрою. Офіційні сторінки TP-Link перевірено під час підготовки документа; вигляд конкретного маршрутизатора потребує ручної перевірки.

### Варіант A – старий класичний зелений інтерфейс

1. Відкрийте `DHCP → Address Reservation → Add New`.
2. У `MAC Address` введіть MAC серверного LAN-адаптера; у `Reserved IP Address` – погоджену адресу.
3. У `Status` виберіть `Enabled` і натисніть `Save`.
4. Перевірте, що запис є в таблиці й увімкнений.

Джерело: [TP-Link FAQ 187](https://www.tp-link.com/uk/support/faq/187/). Колір інтерфейсу сам по собі не визначає точний маршрут.

### Варіант B – новіший інтерфейс

1. Відкрийте `Advanced → Network → DHCP Server → Address Reservation`.
2. Натисніть `Add`, уведіть MAC сервера й погоджену IPv4.
3. Увімкніть запис через `Status` або `Enable This Entry`, залежно від моделі, та збережіть зміни.
4. Переконайтеся, що потрібний запис активний.

Джерело: [TP-Link FAQ 182](https://www.tp-link.com/uk/support/faq/182/). На частині моделей меню починається з `Network`; звіряйте довідник прошивки.

### Варіант C – окремі старі ADSL-моделі

1. Для відповідних моделей відкрийте `Advanced Setup → LAN → Static IP Lease List`.
2. Натисніть `Add`, введіть MAC та погоджену адресу сервера.
3. Натисніть `Save/Apply`, перевірте таблицю та, якщо сторінка цього вимагає, знову `Save/Apply`.

Цей маршрут наведено для Broadcom-моделей, зокрема TD-W8950ND/TD-W8960N: [TP-Link FAQ 488](https://www.tp-link.com/us/support/faq/488/). Він не є універсальним для всіх ADSL-пристроїв.

### Застосування і контроль

> Оновлення оренди перериває мережу сервера; перезапуск маршрутизатора перериває роботу інших користувачів. Погодьте час, закрийте робочі операції та не виконуйте ці дії через єдине віддалене підключення без локальної допомоги.

1. Перевірте збережений MAC, адресу й активність правила. Якщо модель вимагає перезапуску, заплануйте його, попередьте користувачів і виконайте штатну дію маршрутизатора. Не скидайте заводські налаштування.
2. Дочекайтеся оновлення оренди або локально на сервері оновіть її. За кількох адаптерів технічний адміністратор має обмежити команди потрібним адаптером. Для простого ПК з одним LAN-підключенням у командному рядку:

```text
ipconfig /release
ipconfig /renew
ipconfig /all
```

3. Перевірте отриману IPv4, шлюз і доступ до мережі. Якщо сервер отримав іншу адресу, перевірте MAC, DHCP-сервер і вимоги моделі; не задавайте довільну статичну адресу навмання.
4. На робочому місці перевірте порт і `/health`, за потреби перевірте й збережіть нову адресу Client. Перевірте, що область Firewall відповідає адресам клієнтів.
5. Після наступного погодженого перезапуску сервера переконайтеся, що адреса збереглася.

<a id="section-8"></a>
## 8. Віддалений доступ через Tailscale

Tailscale створює захищене з'єднання між дозволеними пристроями. Tailnet – мережа цих пристроїв і користувачів під керуванням організації. HromadaAID не встановлює Tailscale й не керує його користувачами чи правилами. Встановлення: [офіційна інструкція Windows](https://tailscale.com/docs/install/windows).

1. Узгодьте з відповідальною особою використання Tailscale. Створіть організаційну мережу або скористайтеся чинною; визначте її адміністратора.
2. На сервері завантажте офіційний Windows-інсталятор за посиланням у документації Tailscale, запустіть його й підтвердьте права Windows.
3. Біля годинника відкрийте меню значка Tailscale, виберіть `Log in` та завершіть авторизацію в браузері дозволеним обліковим записом.
4. В адміністративній консолі Tailscale перевірте появу серверного пристрою у списку `Machines`. Виконайте потрібне організацією схвалення пристрою.
5. Знайдіть Tailscale IPv4 сервера в цьому списку. Наприклад, `100.101.102.103` належить діапазону `100.64.0.0/10`; це умовний приклад, не адреса вашого сервера.
6. На віддаленому робочому ПК установіть Tailscale за тією самою процедурою. Авторизуйте уповноваженого користувача у потрібному tailnet; не передавайте йому пароль адміністратора організації.
7. Адміністратор перевіряє пристрої та правила доступу tailnet: потрібним користувачам/ПК дозволяється лише необхідний доступ до серверного TCP 4310. На сервері перевірте вузьке правило Windows Firewall за [розділом 6](#section-6).
8. Переконайтеся, що сервер увімкнений, Manager показує доступний локальний API. На віддаленому ПК перевірте з'єднання із фактичною адресою сервера, наприклад:

```powershell
Test-NetConnection 100.101.102.103 -Port 4310
```

9. Відкрийте в браузері віддаленого ПК `http://100.101.102.103:4310/health`. Потім у Client введіть `http://100.101.102.103:4310`, натисніть «Перевірити підключення» та «Зберегти адресу».
10. Увійдіть до HromadaAID своїми обліковими даними й перевірте доступні дані.

Видимість пристрою в tailnet не гарантує доступності API: потрібні служба, дозволений порт і відповідні правила. Про перевірку пристроїв і сервісу: [Tailscale – Connect to devices](https://tailscale.com/docs/how-to/connect-to-devices).

Адміністратор повинен контролювати склад пристроїв, відкликати доступ утрачених ПК/звільнених працівників і застосовувати мінімальні привілеї. Перевіряйте фактичну політику: початкова політика мережі може надавати ширший доступ, ніж потрібний установі. Керування правилами: [Tailscale – Access control](https://tailscale.com/docs/features/access-control).

Для цього сценарію не потрібна публічна переадресація TCP 4310 на WAN маршрутизатора. HTTP HromadaAID між вузлами Tailscale проходить усередині зашифрованого тунелю; напис `http` у Client залишається правильним. Це не додає власного TLS до API й не шифрує окремі звичайні LAN-підключення до того самого сервера.

Якщо доступ зник: перевірте інтернет на обох кінцях, авторизацію/схвалення пристроїв у Tailscale, політику доступу, адресу, Firewall і локальний API сервера. Client автоматично повторює підключення до збереженої адреси, але не перемикається сам на LAN. Відновіть Tailscale або погоджено змініть адресу Client лише після перевірки нового підключення.

<a id="section-9"></a>
## 9. Адміністрування Server Manager

Server Manager запускають локально на сервері. Керування службою й аварійні операції виконуйте з правами адміністратора Windows; резервні операції через API також потребують дозволу в HromadaAID.

| Розділ | Використання |
| --- | --- |
| «Стан сервера» | Стан компонентів, адреси, запуск/зупинка служби |
| «Конфігурація» | Перегляд каталогів і параметрів; це не майстер довільної зміни мережевого порту |
| «Діагностика» | Результати перевірок, причини проблем і технічні подробиці |
| «Резервне копіювання» | Створення, перевірка, експорт, імпорт і відновлення архівів |
| «Оновлення сервера» | Версії Manager/API Server і кероване оновлення |

1. Натисніть «Перевірити зараз» у «Стан сервера».
2. Перевірте окремо Windows Service та API. Служба «Працює» за API «Недоступний» означає проблему; очікуваний підсумок – «Перевірку завершено. Служба працює, API доступний.»
3. Для штатно зупиненого сервера натисніть «Запустити сервер», дочекайтеся результату й перевірте API.
4. Для зупинки або перезапуску попередьте працівників, завершіть їхні операції, натисніть «Зупинити сервер» або «Перезапустити» та підтвердьте запит. Підключені користувачі тимчасово втратять доступ.
5. За помилки відкрийте «Діагностика», збережіть безпечний текст причини та час. Не запускайте паралельно restore й update.

Manager перевіряє локальний http://127.0.0.1:4310/health; це не доводить доступ із іншого ПК. У 1.0.1 автоматичного пошуку адрес немає.

### Ручні адреси підключення

На головному екрані в блоці «Адреси підключення» є три рядки:

| Позиція | Призначення і початкове значення |
| --- | --- |
| Loopback | Адреса для цього комп'ютера; спочатку http://127.0.0.1:4310 |
| LAN | Вручну задана адреса сервера в локальній мережі; спочатку «Не задано» |
| Tailscale | Вручну задана IPv4/DNS-адреса сервера в tailnet; спочатку «Не задано» |

1. Біля потрібної позиції натисніть олівець — праву з двох кнопок.
2. Введіть базову адресу HTTP з портом 4310, наприклад http://server:4310 або фактичну IPv4. Не додавайте логін, пароль, шлях /api, query-параметри чи fragment. HTTPS, IPv6 та 0.0.0.0 не підтримуються.
3. Для Loopback дозволено лише http://127.0.0.1:4310 або http://localhost:4310. Порожній Loopback зберегти не можна.
4. LAN і Tailscale можна очистити: залиште поле порожнім і збережіть; з'явиться «Не задано».
5. Натисніть «Зберегти». «Скасувати» не змінює значення. Сервер не повинен бути доступним у момент збереження; це лише перевірка формату.
6. Для копіювання натисніть ліву кнопку з іконкою Copy. Для «Не задано» вона неактивна. Сам текст адреси можна виділити; повідомлення показує результат копіювання.

Адреси зберігаються у файлі server-addresses.json каталогу
%APPDATA%\HromadaAID-Server-Manager для поточного Windows-користувача.
Вони відновлюються після перезапуску й залишаються при стандартному оновленні
під тим самим користувачем. Якщо файла ще немає, початкові значення показуються
без його автоматичного створення.

Це налаштування відображення й копіювання. Вони не змінюють IP Windows, адаптери,
Tailscale, listener сервера, server.json або збережену адресу Client. Дійсну
адресу визначає мережевий адміністратор через Windows чи консоль Tailscale;
її внесення в Manager не налаштовує доступність мережі.
Навіть після зміни Loopback на localhost внутрішня перевірка Manager залишається
http://127.0.0.1:4310/health; SCM/API перевіряються незалежно.

Якщо файл пошкоджений, несумісний або недоступний, Manager показує помилку та
блокує звичайне редагування. Початкові значення не записуються поверх старих.
Не видаляйте й не скидайте файл навмання: зверніться до адміністратора для
перевірки причини та збереження наявних даних. Після усунення причини
перезапустіть Manager. За помилки запису модалка залишається відкритою,
попереднє значення не замінюється новим у рядку.

<a id="section-10"></a>
## 10. Резервне копіювання

Автоматичне резервування заплановане щодня о 12:00 за місцевим часом сервера. Для створення копії точно за розкладом сервер має працювати в цей час.

Після запуску сервер також перевіряє останній належний щоденний період: до 12:00 це попередній день, після 12:00 – поточний. Якщо відповідної копії немає й сьогодні ще не створено автоматичної копії, сервер намагається зробити її одразу. Наприклад, запуск о 15:00 після пропущеного полудня може створити копію поточних даних. Це не відновлення стану на вчора чи на 12:00 й не набір копій за всі пропущені дні. Якщо автоматична копія вже створена цього календарного дня, ще одна за звичайним розкладом цього дня не створюється; ручні копії доступні окремо.

У разі помилки резервування або зайнятості механізму виконується до трьох спроб за один цикл із паузою п'ять хвилин. Після вичерпання спроб помилка залишається в журналі, а наступний плановий цикл – о наступній 12:00. Нескінченних повторів і гарантованого успіху немає; після збою перевірте дату останньої копії, діагностику й місце на диску.

Ротація розрахована на 14 останніх автоматичних копій; відповідні автоматичні `.hraid` узгоджуються з цим переліком під час підготовки архівів. Помилки видалення можуть тимчасово залишити старі файли. Ручні копії не входять до ліміту 14 й автоматично не ротуються; старі архіви іншого формату та аварійні ключі не очищуються цією ротацією. Контролюйте вільне місце й фактичну дату останньої копії: напис про розклад сам по собі не підтверджує успішного копіювання.

### Ручна копія і перевірка

1. У Manager відкрийте «Резервне копіювання».
2. У «Вхід адміністратора» введіть логін/пароль користувача HromadaAID із правом керування копіями й натисніть «Увійти». API має бути доступним, служба – працювати.
3. Натисніть «Створити копію», дочекайтеся «Резервну копію створено й перевірено.»
4. У «Архіви резервних копій» перевірте новий запис, дату та розмір. Дія-іконка «Перевірити архів» відкриває перевірку; натисніть «Перевірити» й дочекайтеся результату «Архів перевірено».
5. Для окремого захищеного носія використайте дію «Експортувати архів». Не покладайтеся лише на копії на тому самому фізичному диску, що й база.
6. Щоб перевірити зовнішній `.hraid`, натисніть «Вибрати архів», далі «Вибрати файл». Імпорт перевіряє файл і не замінює робочу базу. Для чужого/старого ключа відкрийте «Використати аварійний ключ» та введіть ключ саме цього архіву.

`.hraid` – зашифрований резервний архів. Зберігайте його захищено, аварійний ключ – окремо. Не копіюйте відкриту SQLite вручну як штатний спосіб резервування. Перевірка архіву доводить читання/цілісність, але повну можливість відновлення перевіряють на окремому тестовому сервері з технічним адміністратором, а не на робочій базі.

<a id="section-11"></a>
## 11. Відновлення бази даних

> **Усі зміни після дати вибраної копії буде втрачено.** Поточні дані замінюються. Погодьте дату й перерву з відповідальною особою; повідомте користувачів. Перед запланованим відновленням створіть і експортуйте поточну перевірену копію, якщо сервер працездатний.

### Штатне відновлення через встановлений Manager

1. На сервері запустіть Manager із правами адміністратора Windows, перевірте стан і відсутність незавершених операцій.
2. Відкрийте «Резервне копіювання» й увійдіть із чинним дозволом керування копіями. Оберіть перевірений серверний архів або імпортуйте `.hraid` за [розділом 10](#section-10).
3. Перевірте дату/походження архіву й наявність відомого активного адміністратора в даних, які відновлюються. Старий архів без дати не застосовуйте без встановлення його походження.
4. Виберіть дію «Відновити базу» біля архіву або «До відновлення» після перевірки. За потреби введіть аварійний ключ саме цього архіву.
5. У «Відновлення бази даних» прочитайте попередження «Поточні дані сервера буде замінено даними з вибраної резервної копії. Під час відновлення сервер буде тимчасово недоступний.» Це означає втрату змін після дати архіву; окремого підтвердження кожної втраченої зміни немає. Після погодження заміни підтвердьте кнопкою «Відновити базу».
6. Дочекайтеся завершення. Manager повторно перевіряє архів, штатно зупиняє Windows Service, викликає вбудований offline CLI (службовий інструмент командного рядка), відновлює базу зі страховою копією, запускає службу й перевіряє API. Самостійно вводити CLI-команди в штатному сценарії не потрібно.
7. Перевірте повідомлення «Базу даних відновлено, перевірено та запущено.», свіжий стан служби/API й версію. Усі користувачі входять повторно. Перевірте потрібні записи та звіти на дату копії.

Після відновлення чинні облікові дані можуть бути тими, що містилися в архіві. Страхові копії й збережений початковий файл також містять чутливі дані; не переміщуйте їх у загальнодоступні каталоги.

### Без API та після переривання – для технічного адміністратора

1. Якщо API недоступний, але інсталяція й шляхи підтверджені, локальний адміністратор Windows може відкрити «Аварійне відновлення без API», імпортувати/перевірити архів і виконати підтверджене відновлення. Це не засіб обходу невідомого стану інсталяції.
2. Якщо Manager виявив перервану операцію й дозволяє «Продовжити відновлення», ця дія продовжує її за журналом; новий архів не обирається. Технічний адміністратор має спершу переглянути причину та підтвердити дію.
3. «Повернути попередню базу» можливе лише коли перевірки підтверджують незмінність даних і придатність збереженої попередньої бази, а API ще не підтвердив роботу після restore. Після такого підтвердження або зміни даних повернення блокується. Це не універсальна кнопка скасування й не гарантія повернення будь-якої бази.
4. Якщо потрібна ручна CLI-процедура, зупиніться й передайте її технічному адміністратору. У [технічному описі відновлення](backup-restore.md) є також сценарій розробницького запуску з pnpm: його приклади шляхів і команди не слід переносити дослівно на встановлену робочу систему. Для неї Manager використовує комплектний runtime і фактичні шляхи.

API може блокувати роботу в maintenance – режимі обслуговування під час незавершеного відновлення. Підтвердження плану саме по собі не завершує offline-операцію. Не запускайте сервер навмання й не видаляйте ознаки maintenance, блокування або журнал для обходу перевірок.

### Коли припинити самостійні дії

Залучіть технічного адміністратора, якщо архів не перевіряється, ключ відсутній/не підходить, інсталяція не визначена, схему бази відхилено, журнал пошкоджений, одночасно залишилися restore/update, службу неможливо безпечно зупинити або результат не підтверджено. Не видаляйте й не перейменовуйте службові файли, не підміняйте базу через Провідник. Після помилки CLI служба може залишитися зупиненою для безпеки.

Перед застосуванням небезпечних операцій на робочих даних рекомендується на ізольованій Windows VM перевірити штатне відновлення, роботу реальної служби та її прав, відновлення без API, продовження перерваної операції й доступність/відмову повернення бази. Повне відновлення після втрати сервера та ручну CLI-процедуру також спочатку перевіряйте в ізольованому середовищі з технічним адміністратором. Захист від збоїв не гарантує rollback за довільного стану чи після нових записів.

<a id="section-12"></a>
## 12. Оновлення HromadaAID

> Погодьте перерву й створіть перевірену копію. **Спочатку оновлюйте Server Manager, потім API Server.** Client має власне оновлення. Оновлення API Server перериває доступ усіх користувачів; вибіркове оновлення Manager саме по собі не зупиняє API Server.

### Client

1. Client перевіряє опублікований Stable у GitHub. Після підтвердження новішої версії показує «Потрібно оновити HromadaAID»; продовження роботи потребує оновлення.
2. Натисніть «Оновити зараз». Дочекайтеся завантаження Setup і перевірки цілісності. За помилки доступна «Повторити завантаження».
3. Після готовності натисніть «Закрити Client і продовжити». Підтвердьте UAC, пройдіть майстер Setup й закрийте його «Готово».
4. Дочекайтеся автоматичного відкриття Client. Перевірте встановлену версію у відомостях про застосунок і вхід/доступ до даних. За відмови UAC повторіть оновлення після отримання прав; обов'язковість підтвердженого оновлення зберігається.

### Server Manager

1. Відкрийте «Оновлення сервера» → блок `Server Manager` → «Перевірити оновлення».
2. Перевірте встановлену/доступну версії. Натисніть «Завантажити оновлення Manager» й дочекайтеся перевірки Setup.
3. Натисніть «Оновити зараз», підтвердьте UAC і завершіть Setup. Вибіркове оновлення Manager зберігає склад компонентів і не оновлює API замість вас.
4. Після перезапуску Manager перевірте його встановлену версію у цьому самому блоці й виконайте «Перевірити зараз».

### API Server

1. Перевірте наявність копії, справний/визначений стан інсталяції та відсутність інших транзакцій. Manager має бути саме версії цільового релізу; невідома чи інша версія блокує автоматичне серверне оновлення.
2. У блоці `HromadaAID API Server` натисніть «Завантажити оновлення». Альтернатива – отримайте відповідний Server ZIP з офіційного релізу та натисніть «Вибрати ZIP-файл».
3. Дочекайтеся перевірки ZIP, маніфестів, цілісності, версії, API Contract і сумісності схеми бази. Пакет тієї самої, старішої або попередньої нестабільної версії не є способом штатного downgrade.
4. Прочитайте попередження: Server ZIP не має цифрового підпису. Використовуйте лише довірене джерело; перевірка хешів доводить цілісність, а не особу видавця.
5. Перевірте поточну/нову версії й натисніть «Встановити оновлення». Manager готує пакет, зупиняє службу, активує програмні файли, запускає службу й перевіряє API. Конфігурація та робоча SQLite зберігаються окремо від програмного пакета.
6. Після «Оновлення завершено» натисніть «Перевірити стан». Перевірте версії Manager/API, службу, API, вхід Client і наявні дані. Завершіть також оновлення Client, якщо воно запропоноване.

### Помилка оновлення

За помилки завантаження перевірте інтернет і повторіть її штатною кнопкою. За відмови перевірки ZIP отримайте файл повторно з офіційного релізу. Не редагуйте маніфести для обходу перевірки.

Якщо показано «Попередню версію відновлено», перевірте свіжий стан/API та дані. Якщо «Потрібне ручне відновлення», збережіть повідомлення й залучіть технічного адміністратора. Не видаляйте `Server.next`, `Server.previous`, `Server.failed`, попередні каталоги Manager чи журнал оновлення. Дія «Відновити сервер» доступна лише за підтверджених передумов; не запускайте її навмання. Автоматичний rollback не гарантований для всіх збоїв, особливо за несумісної бази або неоднозначного стану. Технічні примітки: [повторна перевірка ZIP-оновлення](server-manager-update-retry.md).

<a id="section-13"></a>
## 13. Усунення несправностей

| Проблема | Можлива причина | Дії | Перевірка результату |
| --- | --- | --- | --- |
| Client не бачить сервер | Мережа, адреса, служба | Перевірте адресу, локальний Manager, потім порт із робочого ПК | `/health` і перевірка Client успішні |
| Неправильна адреса | Loopback на віддаленому ПК, пропущений порт | Введіть фактичну HTTP IPv4/DNS з `:4310`, перевірте й збережіть | Збережена адреса відповідає серверу |
| Сервер вимкнений/спить | Живлення чи режим сну | Локально ввімкніть/пробудіть; узгодьте живлення | Manager і віддалений API доступні |
| Windows Service не працює | Зупинена служба, помилка запуску | «Перевірити зараз», за штатної зупинки «Запустити сервер»; за помилки – діагностика | Служба «Працює», API «Доступний» |
| API не відповідає | Зайнятий 4310, помилка конфігурації/даних | Перевірте локальний health і діагностику; не змінюйте порт | Manager підтверджує API |
| Firewall блокує порт | Немає правила, не той профіль/Scope | Перевірте вузьке правило, програму, адреси, профіль | TCP й API доступні з дозволеного ПК |
| Змінилася IPv4 | Оренда DHCP | Перевірте `ipconfig`, резервування, адресу Client | Адреса стабільна, Client підключається |
| Не працює Tailscale | Інтернет, авторизація, правила, Firewall | Перевірте обидва пристрої, доступ TCP 4310 і локальний API | Віддалений health і вхід успішні |
| Не вдається авторизуватися | Логін/пароль, завершена сесія, права | Перевірте розкладку/регістр, повторіть вхід; зверніться до адміністратора HromadaAID | Вхід із власним дозволеним обліковим записом |
| Не створюється копія | API/служба, права, брак місця | Перевірте сесію адміністратора, стан, вільне місце й причину | Нова копія з правильною датою перевірена |
| Архів не пройшов перевірку | Пошкодження, інший ключ, несумісність | Перевірте походження й ключ, спробуйте іншу збережену копію; не відновлюйте відхилений архів | «Архів перевірено» |
| Невдале оновлення | Пакет, права, незавершена транзакція | Збережіть діагностику; дійте за розділом 12, не очищуйте службові файли | Підтверджений стан/API/версії |
| Сервер у maintenance | Незавершене обслуговування/restore | Дочекайтеся штатної операції; за переривання передайте технічному адміністратору | Операція завершена, повторний вхід працює |
| Версії компонентів не збігаються | Оновлено лише Client/Manager | Звірте цільовий реліз; завершіть Manager, потім API, окремо Client | Для завершеного релізу всі компоненти очікуваної версії |

Перед зверненням по допомогу запишіть версії компонентів, час помилки, безпечний текст діагностики й результати локального/віддаленого health. Не надсилайте паролі, ключі, базу чи архіви з персональними даними у відкриті канали. Не вимикайте Firewall/антивірус і не видаляйте каталоги для «швидкого виправлення».


<a id="section-14"></a>
## 14. Формування платіжних документів

Цей розділ описує можливості підготовленої версії 1.0.1.

1. Відкрийте Client → «Формування відомостей» і виберіть робочий рік.
   Доступні статуси: «Призначено», «В роботі», «Передано до казначейства»;
   рік визначається датою рішення виконкому.
2. Позначте потрібні призначення. Пошук працює за ПІБ; «Вибрати всі видимі записи»
   стосується видимого списку. Раніше позначені записи, приховані пошуком,
   залишаються у виборі. За одну операцію можна передати до 500 призначень.
3. Стовпець «Банк» розміщений між «Вид допомоги» та «Статус».
   Повну довгу назву можна побачити в підказці. «Не вказано» не приховує запис;
   перед формуванням потрібно доповнити картку отримувача й оновити список.
4. Виберіть персональні, зведені або банківські відомості. У модальному вікні
   спочатку вибрані всі банки позначених призначень. Перемикайте окремі плашки
   або «Всі банки». Частковий стан означає, що вибрана лише частина банків.
   Вибір банку не додає непозначених призначень; без банків формування недоступне.
5. Перевірте реактивний підсумок: кількість призначень, документів і суму.
   Види допомоги визначаються позначеними призначеннями — окремого селектора немає.

| Документ | Правило формування |
| --- | --- |
| Персональний список | Окремо для кожної непорожньої комбінації виду допомоги й банку; автоматичні частини до 12 призначень |
| Зведений список | Один документ для кожної непорожньої комбінації виду допомоги й банку |
| Банківська відомість | Один файл на банк, разом для різних видів допомоги |

Кожне призначення є окремим записом, навіть якщо отримувач повторюється.
Кількість у зведеному документі означає призначення, не унікальних фізичних осіб.
Порожні комбінації не створюють файлів.

Для персональних і зведених документів розгорніть картки й заповніть номер,
дату та період. Кнопка «Застосувати дати та період до всіх» копіює ці поля
до всіх поточних документів; номери залишаються без змін. Для документів
з однаковою датою задавайте різні номери, щоб персональні назви не повторювалися.
Введена дата — реквізит документа, а період — текст його заголовка:
вони не є додатковим фільтром призначень і не фіксують фактичну виплату.

Перед запуском Excel застосунок повторно читає дані сервера. Зміна банку,
виду допомоги або доступності призначень зупиняє операцію з вимогою оновити
список і відкрити параметри повторно. Неповні обов'язкові реквізити й колізії
назв також блокують формування; записи не вилучаються з пакета мовчки.

Сформовані персональні списки доступні як XLS/BIFF8 і PDF, зведені — XLSX і PDF.
Для них є попередній перегляд. Банківські результати — окремі XLSX за банками.
Перевірте кількості, суми й назви, потім збережіть кожний потрібний файл
через чинний файловий діалог. Заміна наявного файла потребує стандартного
підтвердження. Якщо збій стався під час створення одного файла, весь поточний
пакет невдалий; частковий пакет не повертається як готовий результат.

Формування потребує Microsoft Excel через Windows COM. Незмінені шаблони:
«Список.xlsx», «Зведений список.xlsx», «ПриватБанк.xlsx».
**Сумісність формату на основі «ПриватБанк.xlsx» з імпортом інших банків
не підтверджена:** узгодьте вимоги відповідного банку перед передаванням файла.

Генерація й збереження документів не змінюють статусів призначень, сум,
дат фактичних виплат або зв'язків обліку й не створюють фінансових записів.
Факт виплати оформлюється окремою обліковою операцією.
