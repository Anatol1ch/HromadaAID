## Рішення Stage 11

Client перевіряє Stable GitHub Releases незалежно від API Server та авторизації.
Обов'язкове вікно оновлення має пріоритет над системними екранами. Client 1.1.1
координує міжконтрактний перехід за цільовим контрактом manifest і свіжою health
перевіркою, повторюючи її безпосередньо перед встановленням. В межах одного
контракту збережено штатну політику оновлення. Цей механізм не змінює поведінку
старих Client заднім числом і не координує ручне встановлення.

Історія оновлень використовує вбудовані Release Notes опублікованих стабільних
версій, GitHub Releases та локальний кеш. Налаштування — глобальне модальне вікно
з п'ятьма категоріями; масштаб і компактне меню зберігаються локально.

Server Manager зберігає правила fail-closed: без журналу автоматичне recovery
заборонене. Залишки можна архівувати лише після перевірок активного пакета,
служби/API, шляхів та конкуренції і підтвердження адміністратора. Файли
переміщуються, не видаляються. Тимчасові Stage 11 Development Preview механізми
видалені; штатні demo-режими Manager та тестові fixtures залишені.

Оптимізацію пакування Stage 11.5 відхилено: залишаються Universal Setup і Server
ZIP; окремі component installers, shared Electron runtime та differential update
не реалізовувалися.

## Stage 11.7 — технічне приймання

- 117 цільових автоматизованих тестів пройшли; два тести, для яких потрібен
  production Server ZIP, пропущені, бо пакування не виконувалося.
- TypeScript Client/Electron/Server Manager пройшов; `pnpm build` і
  `pnpm manager:build` успішні. У Client build лишилося попередження Vite про
  chunk понад 500 kB.
- PowerShell syntax check і `git diff --check` пройшли.
- Локальна синтетична база й seed не очищалися; Git-виключення `.gitignore` та
  `.git/info/exclude` збережені.
- Перевірка реального production ZIP, Windows VM та фактичного оновлення
  1.1.0 → 1.1.1 не виконувалася.

## Наступні релізні кроки

1. Завершити Stage 11.8.2 окремим завданням: підготувати й погодити Release Notes
   1.1.1; до цього не створювати/публікувати їх.
2. Перед релізом запустити чинний CI/CD і перевірити сформовані Universal Setup,
   Server ZIP, release manifest, SHA-256 та відсутність локальних даних/seed.
3. Переконатися, що релізні Release Notes і metadata відповідають погодженим
   матеріалам та фактичним пакетам.
4. Після публікації провести практичне оновлення Client 1.1.0 → 1.1.1 і цільове
   оновлення API Server у дозволеному тестовому середовищі; окремо перевірити
   підключення та робочі дані.
5. Після фактичної публікації оновити README і всі згадки останньої Stable-версії.

Не позначати 1.1.1 опублікованим до завершення відповідних дій. Не змінювати
робочу інсталяцію чи базу автоматично; не виконувати commit/push/release без
окремого дозволу на відповідний крок.
