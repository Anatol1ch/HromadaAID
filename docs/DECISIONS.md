# Прийняті рішення

Це чинні обмеження для наступних завдань. Реалізацію описує
[ARCHITECTURE.md](ARCHITECTURE.md); непогоджені майбутні рішення — [ROADMAP.md](ROADMAP.md).

| Рішення | Причина / наслідок |
| --- | --- |
| Робоча SQLite лише на Server | Client працює через API; жодного автоматичного повернення legacy local mode |
| Зберегти серверні SQL/domain modules у `electron/` до окремого обґрунтованого перенесення | Їх імпортує Server; історичний шлях не означає невикористаний код |
| Окремі Client, API Server і Manager | Робочі функції, зберігання даних і адміністрування мають різні межі та життєві цикли |
| Server-only завжди API + Manager; один універсальний NSIS продукт | Три режими встановлення, один запис Installed Apps, окремі стабільні AppUserModelID й іконки Client/Manager; звичайний Setup показує Welcome перед Components, selective update показує власний Welcome без вибору компонентів |
| Дані, конфігурація, ключі та копії поза програмним пакетом | Modify/Upgrade/Uninstall не повинні знищувати серверний стан |
| Service SID і обмежені ACL замість загального доступу | Політика серверних ACL належить штатному встановленню служби; restore не скидає Backups ACL |
| Backup administration лише в Manager | Client replication/backup UI/IPC вилучені; старі локальні архіви та identity-файли не видаляються |
| Зберегти `.hraid`, AES-256-GCM, DPAPI та аварійний ключ | Сумісність наявних архівів і встановлених систем; ключі не перегенеровуються при оновленні |
| Зберегти migration 28 і `backup_installations` | Таблиця лишається для сумісності, попри вилучення активної Client replication |
| Один SQLite restore engine з CLI і журналом | Manager організовує offline-процедуру; не підміняє її копіюванням активної SQLite |
| Жодного безумовного автоматичного rollback SQLite | Нові записи після restore можуть бути втрачені; повернення потребує перевірених незмінних даних і явного підтвердження |
| Невизначене recovery зберігає всі придатні копії й артефакти | Краще відмовити з причиною, ніж перезаписати останній придатний стан |
| Update через пакетну транзакцію, не поверхневе копіювання | Потрібні previous/failed/next, integrity, schema compatibility, health та crash recovery |
| Same/older/prerelease ZIP відхиляються звичайним update | Recovery незавершеної транзакції є окремою операцією й не блокується звичайною перевіркою версії |
| Служба Running, API ready та SQLite restored — різні факти | UI не показує повного успіху лише за одним із них |
| Timeout не дорівнює завершенню дочірнього процесу | Lock утримується до підтвердженого завершення дерева; невизначеність блокує нові критичні дії |
| Внутрішній API має один IPv4 HTTP listener 0.0.0.0:4310 | Один Fastify і одна SQLite доступні через loopback, LAN та Tailscale. Порт фіксований, внутрішнього TLS й вибору інтерфейсу немає. LAN HTTP не шифрується; Tailscale надає тунель. Authentication/RBAC/server-side authorization збережено; зовнішній HTTPS не змінено |
| server.json має лише актуальну схему v3 | configVersion: 3, programDirectory, databasePath, backupDirectory. Версії 1/2 та транспортні поля несумісні; автоматична міграція, перезапис і скидання даних заборонені. Спеціального повернення до старого HTTPS немає; загальний update/rollback збережено |
| Адресу сервера задає користувач Client | HTTP IPv4/DNS на порту 4310, збереження між запусками та повторне підключення до того самого сервера. Новий origin перевіряється перед збереженням; credentials і tokens не пересилаються через redirects. Автоматичного пошуку або перемикання серверів немає |
| Історичне рішення Stage 9.2: автоматичні адреси на основному екрані Manager (замінене в 1.0.1) | LAN визначається з фізичних адаптерів Windows, Tailscale — з метаданих адаптера, а не лише CGNAT-діапазону. У 0.2.1 автоматичне визначення LAN/Tailscale IPv4 може бути некоректним у деяких Windows VM; власник прийняв це некритичне обмеження, ручне введення адреси Client збережено. Майстер: каталоги → адміністратор → підсумок; SCM і локальний HTTP health перевіряються окремо |
| 1.0.1: групувати за стабільним banks.id | Персональні/зведені — aidTypeId + bankId; банківські — bankId. Назва й bank_details.id не є ключами груп; однойменні записи довідника не зливаються |
| 1.0.1: одиниця документа — assignment.id | Повторний ID усувається; різні призначення однієї людини залишаються окремими. Кількість означає призначення; персональні частини — до 12 записів |
| 1.0.1: генерація незалежна від фінансових операцій | Новий серверний snapshot, точні суми в копійках і перевірка складу; жодних змін статусів, paid_on, сум або зв'язків. Помилка файла скасовує поточний пакет |
| 1.0.1: адреси Manager вводяться вручну й зберігаються в його userData | Окремий server-addresses.json, послідовний атомарний запис; помилки читання не означають відсутність файла й не дозволяють автоматичний reset |
| 1.0.1: ручні адреси Manager — лише відображення та копіювання | Не змінюють listener, server.json v3, Windows networking, Tailscale чи Client. SCM/API й фіксований локальний health-check незалежні |
| 1.0.2: персональний список використовує адресу проживання | Генератор читає структуровані `residence_*` або legacy `recipients.address`; відсутність адреси блокує експорт і не підміняється реєстраційною. Шаблон не змінено; його заголовок «Адреса реєстрації» не відповідає вмісту, виправлення заголовка окреме |
| 1.0.2: персональні суми лишаються числовими Excel-значеннями | Для G13:G25 встановлюється числовий формат з розділенням тисяч і двома десятковими знаками; суми обліку й формула G25 не змінюються |
| 1.0.1: відмова від автоматичного пошуку LAN/Tailscale | Windows-збір адрес і його типи/тести вилучені; історичне рішення Stage 9.2 збережене вище як замінене |
| Tailscale і Windows Firewall налаштовуються зовні HromadaAID | Немає Tailscale SDK/API, автоматичного встановлення чи керування tailnet/firewall. API запускається без Tailscale, інтернету й конкретного LAN IP; мережеве приймання потребує окремих доступних вузлів |
| Автооновлення використовує лише Stable GitHub Releases і спільний SemVer | Репозиторій береться з явного `release-channel.json`; HTTPS і SHA-256 перевіряють транспорт та цілісність, але не доводять видавця. Токени, Beta/Preview/Nightly, окремий сервер оновлень і система підписів не додаються |
| Client оновлюється чинним універсальним NSIS через окремий Client-only режим | Потрібно зберігати вибір компонентів, Installed Apps запис і сервер у Combined-інсталяції; файлова заміна серверних компонентів з Client заборонена |
| Джерело коду та релізів — публічний `Anatol1ch/HromadaAID` | Окремий release repository не створюється. Власник дозволив публікацію власної контактної картки; через неї не змінювати UI та не переписувати Git history |
| `release/` — тимчасове сховище локальних артефактів збірки | Для кожної версії автоматично створювати окремий `release/<version>/` (наприклад, `release/0.1.4/`) із Setup, Server ZIP, manifest, release notes та іншими потрібними файлами. Не покладатися на попередні версії або зберігати їх як архів; після перевіреної публікації власник може видаляти локальні артефакти. Не відновлювати 0.1.0–0.1.3 без окремої потреби. |
| Три owner-approved Excel templates лишаються tracked runtime assets | `Список.xlsx`, `Зведений список.xlsx`, `ПриватБанк.xlsx` знеособлені й підтверджені власником; повторно не оцінювати їхні дані. Видалений `Реєстр.xlsx` не відновлювати; інші локальні документи не включати автоматично |
| Electron закривається лише після підтвердженого handoff незалежному launcher | Спільний короткий PowerShell bootstrap підтверджує readiness і власне завершення; launcher перевіряє NSIS exit, свіжий marker поточної спроби й версію EXE перед restart |
| Після підтвердження новішого релізу Client вимагає оновлення | До підтвердження мережевої доступності Client працює; після нього metadata зберігаються локально й не дозволяють пропускати версію. UAC відмова дозволяє повторити спробу, але не роботу зі старим Client |
| Оновлення Server Manager використовує окремий режим чинного універсального NSIS | `/MANAGERUPDATE=1` змінює лише каталог Manager, зберігає склад компонентів/Installed Apps і не торкається Windows Service та серверних даних; підтвердження UAC і повторний запуск виконує спільний зовнішній launcher |
| API Server автоматично оновлюється лише Manager тієї самої версії релізу | Оновлення Manager має завершитися першим; несумісна або невідома версія Manager блокує серверний ZIP. ZIP передається чинній транзакції й recovery; служба зупиняється лише після підтвердження адміністратора |
| Менеджерський Upgrade стадіює payload і зберігає попередній каталог під час swap | `/MANAGERUPDATE=1` використовує `ServerManager.next` і `ServerManager.previous`; NSIS відновлює попередню папку після перерваного rename. Після видалення previous-folder повного rollback не гарантовано; це перевіряється у Windows VM |
| Manager у Setup зберігає власні installer/recovery helpers без другого Server runtime | Потрібний `resources/server-payload/installer` та його module graph; API ZIP і далі передається чинній транзакції, missing journal не дозволяє автоматичний recovery |
| Selective update синхронізує ярлики за встановленим набором компонентів | Manager-only зберігає Client-ярлики, Client-only — Manager-ярлики; звичайний Modify/Uninstall видаляє лише належні ярлики з перевіреним target. API ZIP update ярликами не керує |
| Stage 9.5: заповнений МФО перевіряється автоматично й блокує збереження, якщо не містить рівно шість цифр | Перевіряти також на серверному рівні; не змінювати чинну обов'язковість/необов'язковість поля й не перевіряти існування банку через зовнішні джерела |
| Stage 9.5: ЄДРПОУ автоматично перевіряється як рівно вісім цифр і блокує збереження за помилки | Початкові нулі допустимі; контрольний розряд не перевіряється; зовнішні API/довідники не використовуються |
| Stage 9.5: IBAN перевіряється добровільно лише за кнопкою «Перевірити IBAN» | Перевіряти український формат і MOD 97; не запускати автоматично й не блокувати збереження. Успіх не підтверджує існування рахунку чи його належність отримувачу; API НБУ/банків не використовувати |

Зміна цих рішень потребує явної необхідності в завданні, аналізу сумісності й
цільових перевірок. Цей документ не є дозволом змінювати робочі дані або систему.
