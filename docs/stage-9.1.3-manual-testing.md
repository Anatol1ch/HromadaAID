# Stage 9.1.3 — інструкція ручного тестування

## Актуальне приймання Stable 0.1.6 — завершено

Власник підтвердив у Windows 10 x64 VM основні сценарії Stage 9.1:

- Client автоматично оновлено до 0.1.6.
- Server Manager автоматично оновлено з 0.1.5 до 0.1.6.
- API Server оновлено до 0.1.6 через Server Manager.
- Windows Service працює, API доступний, Client authorization успішна, наявні дані збережені.
- Версію 0.1.6 підтверджено для всіх компонентів; створено snapshot
  `HromadaAID 0.1.6 – Stable Baseline`.
- Stable GitHub Release 0.1.6 опубліковано.

**Stage 9.1 прийнято й завершено** на підставі цих основних реальних сценаріїв.
Розширені негативні, аварійні та стресові тести не входили до погодженого обсягу
приймання. Це не є твердженням, що кожен окремий журнал, усі файли даних,
ярлики, DPI або кожен failure path перевірялися у VM.

Усі наступні розділи — історія тестових планів, результатів і виправлень на
попередніх версіях. Їхні тодішні `PENDING`/`FAIL` не описують поточний статус
приймання 0.1.6 і не є відкритим backlog Stage 9.1.

## Межі та підготовка

Stable Release **0.1.0** опубліковано й використано як базову версію. На чистій
Windows 10 x64 VM перевірено початкове Combined встановлення та основні функції
Client, Server Manager й API Server; у цьому сценарії виявили блокування
первинного setup з нестандартними Data/Backups. Виправлення включено до локально
підготовленого комплекту **0.1.1** у `release/stage-9.1.3/stable-0.1.1/`.
Setup, Server ZIP та `release-manifest.json` описують лише фактично зібрані
артефакти; Client portable ZIP не входить до release contract.

Stable Release **0.1.1 опубліковано**. Перевірте його актуальний manifest/assets
перед тестом; лише реальний запуск із GitHub рахується як hosted update.

Комплект Stable **0.1.2 опубліковано** у
`release/stage-9.1.3/stable-0.1.2/`: production Universal Setup, Server ZIP,
release manifest і release notes. Під час першого чистого встановлення у Windows 10
x64 VM підтверджено FAIL первинного налаштування API Server: Manager шукав
`package-integrity.json` у helper-only `ServerManager/resources/server-payload`, тоді
як повний пакет знаходився в `Server.next`. Реєстрація служби й створення `server.json`
не відбулися, бо wizard заблокувався раніше; API health не перевірено.

Stable **0.1.3 hotfix** без функціональних змін зібрано локально зі штатного
production workflow. Payload resolver має цільові regression tests; manifest та
пакети локально перевірені. Це не VM PASS і не публікація. Перед публікацією
потрібні чисті Server-only і Combined VM tests із перевіркою первинного wizard,
конфігурації, Windows Service та API health.

### Історична регресія ярликів після selective update — тоді VM повторний тест очікувався

Після локального Manager-only Setup та успішного за повідомленням власника API
ZIP update у Combined зникли Client-ярлики. Client EXE працює; InstalledComponents
лишається `Client,Server,ServerManager`. Відсутність ярликів підтверджено лише
після обох операцій. Кодом виявлено Manager-only виклик synchronizer з
ClientSelected=0; API ZIP update ярликами не керує. У source прапорець виправлено
на основі InstalledComponents. Поточні зібрані Setup цього виправлення не містять.

Для повторної перевірки потрібні snapshot Combined 0.1.0 та новий локальний Setup:

1. До update зафіксувати обидва ярлики Client/Manager у Public Desktop і Common
   Programs, їхні targets, InstalledComponents та єдиний Installed Apps запис.
2. Виконати `/MANAGERUPDATE=1`; **відразу до API ZIP update** перевірити, що всі
   чотири ярлики існують, запускають відповідні EXE, metadata збережені.
3. Виконати API ZIP update та повторити перевірку ярликів; вони мають зберегтися.
4. На відновленому Combined snapshot окремо виконати `/CLIENTUPDATE=1` і перевірити
   збереження Manager-ярликів. Звичайний install/Modify має створювати/видаляти
   лише ярлики відповідно до встановленого набору компонентів.

Критерій успіху — ярлики обох установлених компонентів доступні після кожної
операції, targets і InstalledComponents коректні, Installed Apps запис один.
Статус цього виправлення: **Не перевірено у VM**, автоматичні цільові tests 14/14 PASS.

### Історичний VM-тест 0.1.0 → 0.1.1 до виправлення bootstrap

- Client і Server Manager виявили стабільну версію 0.1.1.
- Client завантаження спершу завершилося timeout приблизно на 80%; повторна спроба
  завантажила Setup, а SHA-256 перевірка пройшла.
- Після підтвердження Client закрився, але вікно NSIS не з'явилося. Уточнено, що
  невідомо, чи був створений процес Setup; успішне встановлення не підтверджено.
- Manager завантажив Setup і почав перевірку SHA-256; встановлення не завершилося,
  вікна NSIS не спостерігали. Точний результат SHA-256/створення процесу не
  підтверджений.
- API Server ZIP update не тестувався.

Для наступних діагностичних спроб передбачений стійкий журнал
`updates/installer-launcher.log` у user data каталозі Client/Manager; код також
пише файлові stdout/stderr. Журнали можуть містити локальні шляхи, тож перевіряйте
їх перед передаванням. Наявність конкретних записів у логах успішного повного
Client тесту не аналізувалася: власник свідомо не збирав ці журнали.
Bootstrap підтверджений попереднім no-NSIS VM-тестом (U00), а повне встановлення
Client — пізнішим успішним U01 нижче.

### Діагностика передачі керування — 2026-10-26

Історичні підтверджені власником VM-результати до виправлення: discovery Client/Manager — **PASS**;
Client download — **нестабільно (timeout, retry успішний)**; Client installation —
**FAIL**; Manager installation — **FAIL**; API Server update — **NOT TESTED**.
PowerShell PID 7692 (parent 7456) працював ~734 мс та завершився з exit 0.
`launcher-started` немає; запуск NSIS не підтверджено. Ручний запуск справжнього
launcher з Notepad підтвердив binding, запис у TEMP, UAC і роботу скрипту.
Доступ PowerShell до основного APPDATA journal у VM ще не перевірено.

Локальна причина відтворена на Windows PowerShell 5.1.26100.9444 з Node 24.22.1
та Electron 44.7.1 у режимі Node: `detached:true` дає exit 0 без виконання тіла
`.ps1`, зокрема з абсолютним шляхом EXE. `windowsHide` / `-WindowStyle Hidden`
у матриці не визначали результат. Відмова всередині console initialization
узгоджується з відтворенням, але її внутрішній стек не отримували.
Недетачений PowerShell виконує скрипт, проте гине з Node-батьком через libuv Job
Object. Зовнішній Job Object у VM залишається неперевіреною гіпотезою.

Поточний код використовує короткий bootstrap і незалежний launcher через
Start-Process. Electron чекає readiness і завершення bootstrap; файл
handoff.confirmed дозволяє launcher продовжити. Просте створення PID більше не
дозволяє закрити застосунок. SHA-256, RunAs, selective update і success marker
збережені. Bootstrap виправдовується двома відтвореними відмовами прямого spawn;
власного installer engine він не містить.

**Попередній no-NSIS сценарій (bootstrap PASS; не повне встановлення):**

1. Snapshot Windows 10 x64 VM з офіційним Combined 0.1.0 і синтетичними даними.
   Закрийте Client. Візьміть ZIP і README з
   `release/diagnostics/stage-9.1.3/launcher-handoff-v2/`; старі diagnostic ZIP
   для цього сценарію не підходять.
2. За README розгорніть лише Client payload у фактичний NSIS каталог Client,
   запустіть Client звичайним користувачем. Версія має бути 0.1.0. Дочекайтеся
   GitHub Stable 0.1.1, завантаження справжнього Setup та штатної SHA-256 перевірки.
3. Натисніть встановлення один раз. Цей діагностичний launcher навмисно **не має
   виклику NSIS або перезапуску Client**. UAC не очікується. Client має закритися
   лише після ready handoff; після виходу має з'явитися `diagnostic-no-installer`.
4. Збережіть `%APPDATA%\HromadaAID\updates\installer-launcher.log` і всю нову
   папку `updates\launcher-<uuid>`. Вона містить stdout.log, stderr.log,
   bootstrap.stdout.log, bootstrap.stderr.log, config.json (точна command line),
   ready.json, result.json (PID/status/ранній exit code) і handoff.confirmed.
   За потреби додайте повний короткий ProcMon PML із process/file events.
5. Критерій цього тесту: result.status=ready, збіг launcher PID із ready.json,
   у stdout є launcher-started, application-exited, diagnostic-no-installer і
   launcher-completed після закриття Electron. `main-log-write-failed` у stderr
   означає окрему помилку основного журналу. exit 0 без ready — відмова, не успіх.
   При readiness timeout Client має лишитися відкритим; Setup не авторизовано.
6. Відновіть snapshot після збереження результатів. Цей тест не доводить UAC,
   NSIS, auto-restart або успіх встановлення. Їх перевіряти окремо після аналізу.

Власник підтвердив виконання цього сценарію у Windows 10 x64 VM:
`result.status=ready`, launcher PID **7044**, bootstrap PID **9136**,
`exitCode=null` на момент readiness, `handoff.confirmed` присутній. Отримано
`launcher-started`, `waiting-for-application-exit`, `application-exited`,
`diagnostic-no-installer`, `launcher-completed`. **PASS стосується лише bootstrap
і роботи незалежного launcher після виходу Electron.** Реальні UAC, NSIS,
selective update, success marker і restart у цьому тесті не виконувалися.
Попередні 22/22 автоматичних перевірки не підміняють це підтвердження власника.

### Повний Client integration test — PASS (результат зафіксовано 2026-10-27)

Власник успішно використав ZIP
`release/diagnostics/stage-9.1.3/full-update-test/HromadaAID-Client-FullUpdateTest-0.1.0-win-x64.zip`
і README поруч із ним. Це свіжа ізольована збірка Client 0.1.0 з повним production
launcher; обмеження diagnostic-no-installer відсутнє. Main source на момент тесту був 0.1.1,
на момент тесту виправлений updater був у незакоміченому коді; під час подальшої
консолідації його зафіксовано локальними комітами. Опублікований Stable 0.1.1 не
змінювався; тест установив саме офіційний Client цього релізу.

Перед пакуванням додано перевірки свіжості marker поточної спроби й ProductVersion
встановленого EXE. Exit 0, старий marker або правильний marker з EXE 0.1.0 не є
успіхом. Windows ProductVersion 0.1.1.0 відповідає SemVer 0.1.1. Неможливість
видалити marker із Program Files журналюється, ACL не змінюються; потрібен його
новий запис після початку поточної спроби. Помилка автоматичного restart показує
інструкцію відкрити штатний ярлик; факт успішного встановлення зберігається окремо.

**Підстава PASS — безпосереднє підтвердження власника про Windows 10 x64 VM.**
Початковий стан — офіційний Combined 0.1.0 із налаштованим API Server.
Підтверджено розгортання тестового Client 0.1.0, виявлення справжнього GitHub
Stable 0.1.1, завантаження й перевірку пакета, коректне закриття Client,
стандартний Windows UAC, запуск справжнього NSIS, завершення встановлення,
автоматичний restart та встановлену версію Client 0.1.1.

Після встановлення контрольний PowerShell-скрипт із README повернув:

```text
PASS: Client 0.1.1, success marker, Server/Manager files and API Service preserved.
```

Скрипт підтвердив ProductVersion, що відповідає 0.1.1, правильну версію success
marker та його створення/оновлення після початку тесту. InstalledComponents,
контрольні SHA-256 файлів Server/Manager і стан/PID API Service до/після не
змінилися. **U02 PASS лише в цьому обсязі**: повна цілісність SQLite, усіх
серверних даних і безперервність API health протягом оновлення не підтверджені.

**Журнали успішного тесту свідомо не збиралися й не аналізувалися.** Не підтверджено
окремою перевіркою наявність `elevation-requested`, `installer-process-created`,
`installed-component-verified`, `update-confirmed`, `application-restarted` або
`launcher-completed` саме в логах цього повного тесту. PASS установлено за
фактичним результатом, версією, marker і контрольним скриптом. Не виводити з нього
неперевірені подробиці внутрішніх подій, візуального прогресу чи негативних тестів.

Наступні перевірки — повний Manager GitHub update, окреме збереження API даних,
виправлення ярликів та
окремі UAC cancellation/retry і failure/recovery сценарії. Stage 9.1.3 і Stage 9.1
не завершені; production readiness не заявляється.

Перед початком:

1. Використовуйте окрему Windows 10/11 x64 VM зі snapshot. Не встановлюйте ці
   пакети на робочу машину.
2. Для першого встановлення підготуйте чистий snapshot, достатньо місця на
   системному диску та адміністраторський обліковий запис для UAC. Для сценаріїв
   оновлення/відновлення створіть окремі VM зі штучними тестовими даними та
   відновлюваними snapshot-ами.
3. Зафіксуйте версії, назви файлів і SHA-256 з локального release manifest.
   Результати до таблиці вносить тестувальник лише після фактичного виконання.
4. Для Server-only та Combined виділіть окремі адреси/порти для тестового API;
   не використовуйте production SQLite, конфігурації, ключі або backup.
5. Перевірте початковий snapshot перед кожним деструктивним або аварійним
   сценарієм. Переривання NSIS, ZIP-транзакції, Service чи мережі виконуйте лише
   у VM із тестовими даними.

### Що можна перевірити локально без GitHub Release

- Створення Setup і Server ZIP, а також Manager portable runtime directory, який
  потрібен для універсального Setup. Client portable можна пропустити.
- Версії та runtime payload, NSIS compilation і статичні Client-only/
  Manager-only regression checks.
- SHA-256/розміри, локальний release manifest і server package integrity.
- SemVer, Stable filtering, збої завантаження/цілісності та транзакційні сценарії
  у синтетичних автоматичних тестах.
- Початкове встановлення у VM з локальними файлами, якщо для нього не потрібна
  мережна перевірка релізу.

### Що потребує справжнього GitHub Stable Release

- Перевірка доступності релізу в застосунках, отримання опису та manifest із
  GitHub, download прогрес реального asset і його checksum через мережу.
- Обов'язковий Client/Manager update gate, порядок Manager → API Server,
  повторна спроба після тимчасової відмови та повторний запуск після встановлення.

## A. Початкове встановлення (локально, без GitHub Release)

- **Успіх:** Manager завершує первинне налаштування, SCM показує службу, а API

### A03 — Combined

- **Початкові умови:** окрема чиста VM і Setup 0.1.0.
- **Дії:** виберіть Combined, підтвердьте UAC, завершіть setup Server Manager та

- **Очікувано:** встановлено Client, Manager і API Server; дані розташовані поза

- **Успіх:** усі три компоненти запускаються, існує один запис Installed Apps і

#### Виявлений дефект і повторна перевірка нестандартних каталогів

У чистій Windows 10 x64 VM на опублікованому Setup 0.1.0 після Combined
встановлення первинне налаштування з `Data = D:\HromadaAID-Data` та
`Backups = E:\HromadaAID-Backups` блокувалося загальним повідомленням про наявну
або неповну інсталяцію. Підтверджена причина в коді: перевірка відновлення
підготовленого первинного пакета вимагала, щоб Data/Backups збігалися з HKLM
locator, який Setup записує до вибору шляхів у Manager. Для чистого встановлення
ці значення є початковими підказками, а не фактично налаштованими шляхами.

У вихідному коді перевірку змінено: каталог програми й перевірений staged package
мають збігатися, а попередні locator та вибрані Data/Backups дозволені лише коли
відсутні або порожні. Будь-які файли в них, службовий update journal, активний чи
recovery package і неперевірена структура й далі блокують первинну ініціалізацію.
Автоматичне очищення не виконується.

**Статус виправлення у VM: PASS у підтвердженому обсязі.** Власник підтвердив
успішне встановлення Universal Setup 0.1.1 у чистій Windows 10 x64 VM, первинне
налаштування API Server з Data `D:\HromadaAID-Data` і Backups
`E:\HromadaAID-Backups` на різних дисках та працездатність встановленої системи.
Це підтверджує виправлення custom-directory сценарію. Не вважаються перевіреними
окремі Client-only/Server-only режими, відмова UAC, відхилення непорожніх
каталогів або збереження даних під час оновлення. Для повтору на іншому чистому
snapshot використайте Setup 0.1.1 з `release/stage-9.1.3/stable-0.1.1/`;
публікація GitHub для цього початкового встановлення не потрібна. Виберіть
Combined, після встановлення Manager задайте
`C:\Program Files\HromadaAID`, `D:\HromadaAID-Data` і
`E:\HromadaAID-Backups` (попередньо створіть на D:/E: порожні каталоги), завершіть
первинне налаштування й підтвердьте UAC. Успіх: майстер доходить до створення
Service, API health стає доступним, конфігурація вказує на D:/E:, Client
підключається, а SQLite/ключі/файли поза вибраними чистими каталогами не
перезаписуються. Окремо повторіть із непорожнім тестовим Data або Backups: дія має
зупинитися, показати причину й залишити sentinel-файл незмінним.

### A04 — Створення Windows Service

- **Початкові умови:** A02 або A03 успішно встановив файли, але Service ще не
  налаштована; VM snapshot збережений.
- **Дії:** у Manager виконайте первинне налаштування, підтвердіть UAC; перевірте
  Service у Services/SCM.
- **Очікувано:** інстальовано WinSW wrapper із чинним конфігом і захищеними
  тестовими шляхами.
- **Успіх:** Service запускається через Manager, а health API підтверджує
  працездатність; одного статусу Running недостатньо.

### A05 — Перший запуск Client

- **Початкові умови:** Client встановлено через A01 або A03.
- **Дії:** запустіть Client звичайним користувачем; пройдіть наявний перший запуск

- **Очікувано:** UI завантажується без блокування на перевірці релізів; параметри

- **Успіх:** Client можна закрити й відкрити знову, збережені налаштування

### A06 — Перший запуск Server Manager

- **Початкові умови:** Server Manager установлений через A02 або A03.
- **Дії:** відкрийте Manager; виконайте перевірку середовища та необхідне
  початкове налаштування.
- **Очікувано:** Manager показує фактичний стан Service/API; перевірка GitHub без
  опублікованого релізу не заважає локальній роботі.
- **Успіх:** Manager лишається працездатним і після перезапуску, конфігурація
  відображає вибрані тестові шляхи.

### A07 — Підключення Client до API Server

- **Початкові умови:** A03/A04 успішні, тестовий API health готовий.
- **Дії:** у Client задайте адресу API цієї VM та виконайте безпечний тестовий
  запит/вхід за штатним сценарієм застосунку.
- **Очікувано:** запит досягає тестового API, а TLS/auth поведінка відповідає
  конфігурації VM.
- **Успіх:** Client отримує очікувану відповідь від тестового сервера; жодні
  production credentials не використовувалися.

- **Межі:** окремі контрольні записи SQLite, hashes конфігурації, безперервний
  health і негативний recovery цим повідомленням не підтверджені. D01–D12 не
  отримують автоматично PASS на підставі D00.
- **Історія FAIL:** до fix відсутній Manager-owned installer залишив Server.next
  без journal; Service Running зі старим PID та API 0.1.0. Test-Path у VM дав
  False. Після packaging fix основний сценарій успішний; recovery без journal
  і надалі заборонений, жодного автоматичного очищення staging не додано.

### D01 — Виявлення API Server версії

- **Початкові умови:** встановлений API старіший за Stable release; Manager
  сумісної версії.
- **Дії:** запустіть автоматичну або ручну перевірку в Manager.
- **Очікувано:** доступна версія API показана окремо від Manager; Service не
  зупиняється при виявленні.
- **Успіх:** доступна саме новіша Stable версія, а API лишається healthy.

### D02 — Server ZIP download

- **Початкові умови:** D01 підтверджений; стабільна мережа.
- **Дії:** натисніть завантаження API Server і спостерігайте прогрес.
- **Очікувано:** завантажується серверний ZIP з того самого release manifest.
- **Успіх:** повний asset переданий чинному prepare/update flow.

### D03 — SHA-256 та внутрішній integrity manifest

- **Початкові умови:** Server ZIP завантажений.
- **Дії:** дочекайтеся зовнішньої SHA-256 перевірки та чинної перевірки ZIP
  payload/`package-integrity.json`.
- **Очікувано:** package preview з'являється тільки після всіх перевірок.
- **Успіх:** зміна байта або відсутній/невалідний файл відхиляє пакет до Service stop.

### D04 — Попередження про недоступність

- **Початкові умови:** package preview валідний; API обслуговує лише тестовий трафік.
- **Дії:** натисніть установлення та прочитайте попередження.
- **Очікувано:** Manager прямо повідомляє про зупинку Service і коротку
  недоступність системи.
- **Успіх:** Service ще працює, доки адміністратор явно не підтвердить.

### D05 — Підтвердження адміністратора

- **Початкові умови:** D04 показує попередження.
- **Дії:** спочатку скасуйте й перевірте, що Service лишився healthy; повторіть і
  цього разу підтвердьте встановлення.
- **Очікувано:** відміна не зупиняє Service; підтвердження починає транзакцію.
- **Успіх:** зупинка відбулася лише після другої явної згоди.

### D06 — Зупинка Windows Service

- **Початкові умови:** D05 підтверджено; operation lock вільний.
- **Дії:** спостерігайте Manager progress і SCM під час транзакції.
- **Очікувано:** служба штатно зупиняється після перевірок і перед switch.
- **Успіх:** active package змінюється лише через чинний transactional engine.

### D07 — ZIP транзакція та артефакти

- **Початкові умови:** тестова транзакція стартувала.
- **Дії:** дочекайтеся успішного update; після нього перевірте `Server.next`,
  `Server.previous`, `Server.failed` і update-state journal згідно з результатом.
- **Очікувано:** package roles та журнал узгоджені; потрібні recovery артефакти
  не видаляються перед підтвердженим результатом.
- **Успіх:** операція відповідає стану журналу; нічого не «підчищалося» вручну.

### D08 — Автоматичний запуск служби

- **Початкові умови:** D06/D07 завершені.
- **Дії:** дочекайтеся перевірки SCM та API health у Manager.
- **Очікувано:** Service автоматично запускається з перевіреного active package.
- **Успіх:** SCM і API health обидва відповідають; сам Running не зараховується.

### D09 — API health і повідомлення результату

- **Початкові умови:** новий пакет встановлений; API перевіряється.
- **Дії:** прочитайте фінальний стан у Manager та повторіть безпечний API health
  запит.
- **Очікувано:** успіх показано лише для нового активного пакета після health.
- **Успіх:** UI повідомляє фактичний результат, без передчасного успіху після
  download або одного SCM Running.

### D10 — SQLite збережена

- **Початкові умови:** synthetic DB з контрольними тестовими записами та snapshot.
- **Дії:** виконайте успішний update і перевірте цілісність/контрольні записи
  штатними read-only засобами.
- **Очікувано:** ZIP update не замінює й не автоматично відкочує SQLite.
- **Успіх:** тестові записи й схема збережені; автоматичний SQLite rollback не
  заявляється.

### D11 — Конфігурація збережена

- **Початкові умови:** зафіксовані тестові Program/Data/Backup paths, bind/port і
  service config.
- **Дії:** після D09 перевірте ті самі значення та health.
- **Очікувано:** оновлення зберігає зовнішню конфігурацію й persistent data.
- **Успіх:** конфігурація збігається з базовим записом, API доступний.

### D12 — Recovery після server update помилки

- **Початкові умови:** окрема snapshot VM із synthetic DB; помилка/переривання
  відтворюється лише за підготовленим тестовим recovery сценарієм.
- **Дії:** скористайтеся чинними diagnostics/recovery діями; не видаляйте
  `Server.next`, `Server.previous`, `Server.failed` чи journal і не запускайте
  ручне копіювання.
- **Очікувано:** неоднозначність зупиняє автоматичні зміни та зберігає докази;
  recovery перевіряє SCM і API health.
- **Успіх:** результат відповідає recovery decision і підтвердженій готовності API;
  SQLite автоматично не відкочується.

## E. Історичний перелік негативних сценаріїв (поза обсягом приймання Stage 9.1)

E01–E10 виконувати на окремих snapshot VM і тільки з тестовими asset/data. Для
мережевих помилок бажано використовувати контрольований firewall/ізоляцію VM;
не редагуйте робочі release-файли.

### E01 — Відсутність інтернету

- **Початкові умови:** нова інсталяція без раніше підтвердженого update.
- **Дії:** вимкніть мережу VM і запустіть Client/Manager.
- **Очікувано:** асинхронна перевірка завершується зрозумілим станом; застосунок
  продовжує локальну роботу.
- **Успіх:** UI не завис, Service не зупинено автоматично.

### E02 — GitHub недоступний

- **Початкові умови:** контрольований DNS/firewall block до GitHub у VM.
- **Дії:** виконайте ручну перевірку та відновіть мережу.
- **Очікувано:** показана помилка мережі; до підтвердження релізу робота
  продовжується; підтверджений раніше gate не скидається.
- **Успіх:** після відновлення мережі перевірку можна повторити.

### E03 — Перерване завантаження

- **Початкові умови:** потрібен опублікований Stable asset; VM snapshot.
- **Дії:** перервіть мережу VM посеред download.
- **Очікувано:** partial файл не стає готовим пакетом; UI показує помилку й retry.
- **Успіх:** нова спроба після відновлення мережі завантажує/перевіряє повний файл.

### E04 — Пошкоджений пакет

- **Початкові умови:** від'єднана копія тестового пакета у disposable VM.
- **Дії:** змініть один байт у копії після download або використайте спеціально
  підготовлений тестовий asset з невірним digest.
- **Очікувано:** hash або embedded integrity validation відхиляє пакет до запуску
  NSIS/Service update.
- **Успіх:** пошкоджений пакет не встановлено, gate зберігається для retry.

### E05 — Недостатньо місця

- **Початкові умови:** окремий тестовий диск/VM із контрольовано малим вільним
  простором; не заповнюйте робочу машину.
- **Дії:** запустіть preflight або download/update.
- **Очікувано:** конкретна помилка місця до небезпечної заміни; поточний пакет
  і дані збережені.
- **Успіх:** після звільнення місця повтор проходить, recovery-файли не видалені.

### E06 — Відмова UAC

- **Початкові умови:** перевірений Client або Manager Setup готовий.
- **Дії:** відхиліть UAC prompt.
- **Очікувано:** нова версія не оголошується встановленою, обов'язковий gate лишається.
- **Успіх:** повторна спроба доступна, API Server не змінений.

### E07 — Перерване встановлення

- **Початкові умови:** snapshot VM; лише синтетичні дані.
- **Дії:** перервіть installer лише за окремим VM-сценарієм, де це безпечно;
  дочекайтеся процесу/launcher result, потім перевірте стан повторним запуском.
- **Очікувано:** відсутність підтвердження не показує update success; NSIS
  recovery-папки/marker обробляються чинним шляхом.
- **Успіх:** Manager/Client або відновлено, або gate лишився та retry/recovery
  доступні; не заявляється гарантований rollback Manager.

### E08 — Повтор після помилки

- **Початкові умови:** будь-який попередній update failure усунуто у snapshot VM.
- **Дії:** скористайтеся UI retry без ручного видалення transaction artifacts.
- **Очікувано:** послідовна повторна операція, без другого паралельного updater.
- **Успіх:** пакет перевірено знову й фактичний результат відображений.

### E09 — Некоректна версія і prerelease

- **Початкові умови:** синтетичні metadata у локальних automated tests; не
  публікуйте тестовий prerelease.
- **Дії:** запускайте чинні SemVer/Stable filtering tests; у VM використовуйте
  лише окремий контрольований тестовий GitHub Release після дозволу.
- **Очікувано:** некоректний SemVer, та сама/старіша версія та prerelease
  відхиляються.
- **Успіх:** локальний набір підтверджує фільтрацію; hosted behavior позначається
  окремо до виконання реального релізу.

### E10 — Незавершена серверна транзакція

- **Початкові умови:** synthetic Server/Data, snapshot VM і заздалегідь визначена
  recovery-стадія.
- **Дії:** відтворіть тільки дозволену тестову незавершену транзакцію; відкрийте
  recovery/diagnostics, нічого не видаляйте й не змінюйте SQLite вручну.
- **Очікувано:** автоматична операція блокується за неоднозначності; журнали та
  `Server.next`/`previous`/`failed` збережені.
- **Успіх:** чинний recovery визначає дію, потім окремо підтверджуються SCM та API
  health; небезпечного автоматичного SQLite rollback немає.
