# Stage 9.1.3 — інструкція ручного тестування

## Межі та підготовка

Контрольні збірки цього етапу мають версію **0.1.0**. Після оновлення шаблонів
їх потрібно перебудувати, перш ніж поширювати. Актуальні універсальний Setup та
Server ZIP описуються у
`release-manifest.json`; Client portable ZIP і portable Server Manager каталогу
не є основними update-артефактами цього manifest. Client portable є необов'язковим
ручним способом запуску й не входить до обов'язкового Stable release workflow.

Налаштований GitHub repository наразі не має опублікованого Stable release
(перевірка GitHub API повернула HTTP 404 для `releases/latest`). Тому локальна
перевірка пакетів можлива вже зараз, але автоматичне отримання оновлення через
GitHub — ні. Для update-сценаріїв нижче потрібна опублікована пара справжніх
Stable releases з повними узгодженими артефактами та manifest. Збірка 0.1.0 може
бути початковою версією; потрібна новіша версія, наприклад 0.1.1. Її створення,
Git tag і публікація вимагають окремого релізного дозволу. Не підмінюйте їх
локальними файлами чи застарілими пакетами.

Перед початком:

1. Використовуйте окрему Windows 10/11 x64 VM зі snapshot. Не встановлюйте ці
   пакети на робочу машину.
2. Для першого встановлення підготуйте чистий snapshot, достатньо місця на
   системному диску та адміністраторський обліковий запис для UAC. Для сценаріїв
   оновлення/відновлення створіть окремі VM зі штучними тестовими даними та
   відновлюваними snapshot-ами.
3. Зафіксуйте версії, назви файлів і SHA-256 з локального release manifest.
   Результати до таблиці вносить тестувальник лише після фактичного виконання.
4. Для Server-only та Combined виділіть окремі адреси/порти для тестового API;
   не використовуйте production SQLite, конфігурації, ключі або backup.
5. Перевірте початковий snapshot перед кожним деструктивним або аварійним
   сценарієм. Переривання NSIS, ZIP-транзакції, Service чи мережі виконуйте лише
   у VM із тестовими даними.

### Що можна перевірити локально без GitHub Release

- Створення Setup і Server ZIP, а також Manager portable runtime directory, який
  потрібен для універсального Setup. Client portable можна пропустити.
- Версії та runtime payload, NSIS compilation і статичні Client-only/
  Manager-only regression checks.
- SHA-256/розміри, локальний release manifest і server package integrity.
- SemVer, Stable filtering, збої завантаження/цілісності та транзакційні сценарії
  у синтетичних автоматичних тестах.
- Початкове встановлення у VM з локальними файлами, якщо для нього не потрібна
  мережна перевірка релізу.

### Що потребує справжнього GitHub Stable Release

- Перевірка доступності релізу в застосунках, отримання опису та manifest із
  GitHub, download прогрес реального asset і його checksum через мережу.
- Обов'язковий Client/Manager update gate, порядок Manager → API Server,
  повторна спроба після тимчасової відмови та повторний запуск після встановлення.
- Для перевірки оновлення з 0.1.0 потрібен новіший сумісний Stable release.
  Опублікований реліз має містити Setup, Server ZIP та узгоджений
  `release-manifest.json`; prerelease не підходить.

У цьому етапі реліз не створювався. Не позначайте GitHub update-сценарії
успішними на підставі локальних тестів або завантаження файлу вручну.

## A. Початкове встановлення (локально, без GitHub Release)

### A01 — Client-only

- **Початкові умови:** чиста Windows x64 VM; Setup 0.1.0 з каталогу етапу.
- **Дії:** запустіть Setup, виберіть Client-only, підтвердьте UAC, дочекайтеся
  завершення; відкрийте Client.
- **Очікувано:** встановлено лише Client; Client стартує й показує доступний
  екран без помилок першого запуску.
- **Успіх:** Client відкривається з ярлика, а Server Manager, API Service і
  серверні каталоги не створені.

### A02 — Server-only

- **Початкові умови:** окрема чиста VM і Setup 0.1.0.
- **Дії:** виберіть Server-only та підтвердьте UAC. У Server Manager пройдіть
  перше налаштування сервера з тестовими шляхами й тестовим адміністратором.
- **Очікувано:** Server Manager і API Server встановлені; створено Windows
  Service та окремі каталоги даних/backup.
- **Успіх:** Manager завершує первинне налаштування, SCM показує службу, а API
  health відповідає готовністю.

### A03 — Combined

- **Початкові умови:** окрема чиста VM і Setup 0.1.0.
- **Дії:** виберіть Combined, підтвердьте UAC, завершіть setup Server Manager та
  відкрийте Client.
- **Очікувано:** встановлено Client, Manager і API Server; дані розташовані поза
  програмними файлами.
- **Успіх:** усі три компоненти запускаються, існує один запис Installed Apps і
  одна очікувана Windows Service.

### A04 — Створення Windows Service

- **Початкові умови:** A02 або A03 успішно встановив файли, але Service ще не
  налаштована; VM snapshot збережений.
- **Дії:** у Manager виконайте первинне налаштування, підтвердіть UAC; перевірте
  Service у Services/SCM.
- **Очікувано:** інстальовано WinSW wrapper із чинним конфігом і захищеними
  тестовими шляхами.
- **Успіх:** Service запускається через Manager, а health API підтверджує
  працездатність; одного статусу Running недостатньо.

### A05 — Перший запуск Client

- **Початкові умови:** Client встановлено через A01 або A03.
- **Дії:** запустіть Client звичайним користувачем; пройдіть наявний перший запуск
  і задайте адресу тестового API.
- **Очікувано:** UI завантажується без блокування на перевірці релізів; параметри
  зберігаються у призначеному для користувача профілі.
- **Успіх:** Client можна закрити й відкрити знову, збережені налаштування
  лишаються доступними.

### A06 — Перший запуск Server Manager

- **Початкові умови:** Server Manager установлений через A02 або A03.
- **Дії:** відкрийте Manager; виконайте перевірку середовища та необхідне
  початкове налаштування.
- **Очікувано:** Manager показує фактичний стан Service/API; перевірка GitHub без
  опублікованого релізу не заважає локальній роботі.
- **Успіх:** Manager лишається працездатним і після перезапуску, конфігурація
  відображає вибрані тестові шляхи.

### A07 — Підключення Client до API Server

- **Початкові умови:** A03/A04 успішні, тестовий API health готовий.
- **Дії:** у Client задайте адресу API цієї VM та виконайте безпечний тестовий
  запит/вхід за штатним сценарієм застосунку.
- **Очікувано:** запит досягає тестового API, а TLS/auth поведінка відповідає
  конфігурації VM.
- **Успіх:** Client отримує очікувану відповідь від тестового сервера; жодні
  production credentials не використовувалися.

## B. Автоматичне оновлення Client (потрібен новіший Stable Release)

Для B01–B12 початково встановіть Client старішої пари релізу; новіший Stable
release має бути опублікований із повним manifest та Setup. Збережіть копію
налаштувань тестового користувача. Використовуйте окрему VM.

### B01 — Автоматичне виявлення

- **Початкові умови:** старіший Client; GitHub доступний; новіший Stable release
  опублікований.
- **Дії:** запустіть Client і дочекайтеся фонової перевірки.
- **Очікувано:** інтерфейс відкривається до завершення мережевої перевірки, потім
  з'являється gate із поточною й доступною версіями.
- **Успіх:** показана точна новіша Stable-версія, інтерфейс не завис під час
  старту.

### B02 — Обов'язкове модальне вікно

- **Початкові умови:** B01 підтвердив реліз.
- **Дії:** огляньте модальне вікно й спробуйте взаємодіяти з основним UI.
- **Очікувано:** показані обидві версії та короткі release notes; звичайні дії
  заблоковані.
- **Успіх:** користувач розуміє, який пакет і чому потрібно встановити.

### B03 — Немає пропуску чи відкладання

- **Початкові умови:** обов'язкове модальне вікно відкрите.
- **Дії:** огляньте кнопки/закриття модального вікна; перезапустіть Client до
  встановлення.
- **Очікувано:** немає «Пізніше», «Пропустити» чи «Нагадати»; підтверджений gate
  відновлюється.
- **Успіх:** не можна повернутися до звичайної роботи зі старим Client.

### B04 — Завантаження та прогрес

- **Початкові умови:** B01 підтверджений; мережа стабільна.
- **Дії:** натисніть «Оновити зараз», стежте за прогресом.
- **Очікувано:** відображається рухомий прогрес до повного розміру Setup.
- **Успіх:** завантажено повний asset із відповідного release, без завислого
  паралельного запиту.

### B05 — Перевірка пакета

- **Початкові умови:** Setup завантажено.
- **Дії:** дочекайтеся SHA-256/розмір перевірки; у окремому негативному сценарії
  використайте навмисно змінену копію лише в тестовій VM.
- **Очікувано:** коректний Setup переходить до підтвердження закриття; змінений
  пакет відхиляється та дозволяє повторити завантаження.
- **Успіх:** підміна/пошкодження не запускає Setup.

### B06 — UAC підтвердження

- **Початкові умови:** пакет перевірено; налаштування Client збережено.
- **Дії:** натисніть оновлення, підтвердьте UAC.
- **Очікувано:** перед закриттям Client показано попередження про незбережені
  зміни; відкривається чинний універсальний Setup.
- **Успіх:** UAC належно запитує підтвердження, підвищення прав не обходиться.

### B07 — Встановлення Client

- **Початкові умови:** UAC підтверджено.
- **Дії:** дочекайтеся візуального прогресу Setup.
- **Очікувано:** Client-only режим замінює лише Client.
- **Успіх:** Setup завершується з новою версією; конфігураційні та користувацькі
  дані залишилися на місці.

### B08 — Автоматичний повторний запуск

- **Початкові умови:** B07 успішний.
- **Дії:** дочекайтеся запуску програми після Setup.
- **Очікувано:** відкривається оновлений Client, а не старий executable.
- **Успіх:** About/версія показує цільовий реліз і Client реагує на UI.

### B09 — Збереження налаштувань

- **Початкові умови:** до оновлення задані унікальні тестові параметри.
- **Дії:** завершіть B07–B08 і перевірте ті самі параметри.
- **Очікувано:** update не скидає користувацькі налаштування.
- **Успіх:** параметри збігаються з контрольним записом до оновлення.

### B10 — Server у Combined інсталяції

- **Початкові умови:** Combined VM, Service/API healthy, новіший Client release.
- **Дії:** виконайте B04–B08, одночасно спостерігайте Service і API health.
- **Очікувано:** Client-only NSIS не змінює серверні файли і не зупиняє Service.
- **Успіх:** Service/API лишаються healthy до, під час і після Client update.

### B11 — Відмова UAC

- **Початкові умови:** підтверджений gate та завантажений перевірений Setup.
- **Дії:** на UAC prompt виберіть відмову.
- **Очікувано:** старий Client не вважається оновленим; користувач може повторити
  спробу.
- **Успіх:** gate лишається обов'язковим, повторний запуск Setup доступний,
  стан сервера не змінений.

### B12 — Повторна спроба після помилки

- **Початкові умови:** ізольована VM і підтверджений release; створіть тимчасову
  мережеву помилку/недостатній вільний простір лише на тестовому диску.
- **Дії:** запустіть завантаження, зафіксуйте помилку, відновіть мережу/простір та
  натисніть повтор.
- **Очікувано:** причина показана, частковий пакет не запускається, gate зберігається.
- **Успіх:** повторна спроба завершується штатним шляхом після усунення причини.

## C. Автоматичне оновлення Server Manager (потрібен новіший Stable Release)

Для C01–C12 установіть старішу версію у Server-only і Combined VM. Переконайтеся,
що Service, SQLite та тестова конфігурація healthy; створіть snapshot.

### C01 — Виявлення нової версії

- **Початкові умови:** старий Manager, GitHub доступний, новіший Stable release.
- **Дії:** запустіть Manager або дочекайтеся періодичної перевірки.
- **Очікувано:** асинхронно відображається нова версія Manager.
- **Успіх:** перевірка не затримує запуск і показує версії окремо від API Server.

### C02 — Обов'язковість оновлення Manager

- **Початкові умови:** Manager підтвердив нову версію.
- **Дії:** спробуйте відкрити звичайні функції та перезапустіть Manager.
- **Очікувано:** обов'язковий modal блокує штатну роботу та з'являється знову.
- **Успіх:** немає пропуску/відкладання; оновлення можна повторити.

### C03 — Аварійне recovery доступне

- **Початкові умови:** C02 gate активний; тестова транзакція/діагностика доступна.
- **Дії:** виберіть дію аварійного recovery, лише перегляньте стан; не запускайте
  руйнівне відновлення без окремого тестового snapshot.
- **Очікувано:** recovery та діагностика лишаються доступними, звичайні дії — ні.
- **Успіх:** стан неоднозначної операції можна переглянути, артефакти не видалені.

### C04 — Завантаження Manager Setup

- **Початкові умови:** C02 активний; доступ до GitHub стабільний.
- **Дії:** виберіть оновлення і спостерігайте прогрес.
- **Очікувано:** Setup завантажується окремо від Server ZIP.
- **Успіх:** розмір прогресує, інтерфейс лишається чутливим.

### C05 — Перевірка Manager пакета

- **Початкові умови:** Setup завантажений.
- **Дії:** дочекайтеся SHA-256/size verification; для negative test змініть лише
  окрему копію у VM.
- **Очікувано:** коректний asset готовий; пошкоджений відхиляється.
- **Успіх:** невалідний Setup не передається NSIS.

### C06 — Manager-only NSIS

- **Початкові умови:** Manager package перевірений; окрема Server-only або Combined
  VM зі збереженою конфігурацією.
- **Дії:** підтвердьте «Закрити й оновити» та спостерігайте Setup.
- **Очікувано:** універсальний NSIS працює в Manager-only режимі, показує прогрес,
  не змінює Client/Server payload і не запускає їхні setup sections.
- **Успіх:** версія Manager оновлена, конфігураційні каталоги збережені.

### C07 — UAC Manager update

- **Початкові умови:** C06 на екрані UAC.
- **Дії:** підтвердьте запит стандартним адміністраторським способом.
- **Очікувано:** інсталятор отримує штатний UAC; ACL не послаблюються.
- **Успіх:** Setup продовжується після згоди та завершується без обходу UAC.

### C08 — Автоматичний повторний запуск Manager

- **Початкові умови:** C06/C07 успішні.
- **Дії:** дочекайтеся завершення Setup та launcher.
- **Очікувано:** оновлений Manager автоматично відкривається; success marker
  підтверджує завершення Setup.
- **Успіх:** запущена цільова версія й обов'язковий gate знятий тільки після
  підтвердження маркера.

### C09 — Збереження конфігурації

- **Початкові умови:** до update зафіксовані шляхи Data/Backups, URL/порт і стан
  installation.
- **Дії:** після C08 порівняйте значення та відкрийте Manager повторно.
- **Очікувано:** Manager update не переписав конфігурацію чи user data.
- **Успіх:** усі контрольні значення збережені.

### C10 — API Service не зупиняється

- **Початкові умови:** Combined VM; API healthy; Service status/health можна
  спостерігати локально.
- **Дії:** виконайте C06–C08, слідкуйте за Service/API.
- **Очікувано:** Manager-only update не запускає серверні NSIS/service операції.
- **Успіх:** не було stop/reinstall, а API залишався healthy.

### C11 — Installed Apps збережено

- **Початкові умови:** Manager внесений до Installed Apps; зафіксуйте назву,
  версію, uninstall entry та `InstalledComponents`.
- **Дії:** виконайте C06–C08 і перевірте системний запис.
- **Очікувано:** зберігається єдиний запис HromadaAID, версія оновлена, набір
  компонентів не змінений.
- **Успіх:** немає дубльованого запису чи втрати встановлених компонентів.

### C12 — Повтор Manager update після помилки

- **Початкові умови:** snapshot VM; відмова UAC або штучна недостатність місця на
  окремому тестовому диску.
- **Дії:** зафіксуйте безпечний abort, усуньте причину й повторіть update.
- **Очікувано:** попередній Manager або recovery папки не видалені при помилці;
  повторна спроба доступна.
- **Успіх:** тестовий Manager відновлено/оновлено, Server Service та дані цілі.

## D. Оновлення API Server (потрібен новіший Stable Release)

Потрібні Manager тієї самої версії, що й target release, та Server ZIP у його
manifest. Якщо Manager старіший за реліз, спочатку виконайте C-сценарії. Для
кожної VM використовуйте snapshot, synthetic SQLite і backup.

### D01 — Виявлення API Server версії

- **Початкові умови:** встановлений API старіший за Stable release; Manager
  сумісної версії.
- **Дії:** запустіть автоматичну або ручну перевірку в Manager.
- **Очікувано:** доступна версія API показана окремо від Manager; Service не
  зупиняється при виявленні.
- **Успіх:** доступна саме новіша Stable версія, а API лишається healthy.

### D02 — Server ZIP download

- **Початкові умови:** D01 підтверджений; стабільна мережа.
- **Дії:** натисніть завантаження API Server і спостерігайте прогрес.
- **Очікувано:** завантажується серверний ZIP з того самого release manifest.
- **Успіх:** повний asset переданий чинному prepare/update flow.

### D03 — SHA-256 та внутрішній integrity manifest

- **Початкові умови:** Server ZIP завантажений.
- **Дії:** дочекайтеся зовнішньої SHA-256 перевірки та чинної перевірки ZIP
  payload/`package-integrity.json`.
- **Очікувано:** package preview з'являється тільки після всіх перевірок.
- **Успіх:** зміна байта або відсутній/невалідний файл відхиляє пакет до Service stop.

### D04 — Попередження про недоступність

- **Початкові умови:** package preview валідний; API обслуговує лише тестовий трафік.
- **Дії:** натисніть установлення та прочитайте попередження.
- **Очікувано:** Manager прямо повідомляє про зупинку Service і коротку
  недоступність системи.
- **Успіх:** Service ще працює, доки адміністратор явно не підтвердить.

### D05 — Підтвердження адміністратора

- **Початкові умови:** D04 показує попередження.
- **Дії:** спочатку скасуйте й перевірте, що Service лишився healthy; повторіть і
  цього разу підтвердьте встановлення.
- **Очікувано:** відміна не зупиняє Service; підтвердження починає транзакцію.
- **Успіх:** зупинка відбулася лише після другої явної згоди.

### D06 — Зупинка Windows Service

- **Початкові умови:** D05 підтверджено; operation lock вільний.
- **Дії:** спостерігайте Manager progress і SCM під час транзакції.
- **Очікувано:** служба штатно зупиняється після перевірок і перед switch.
- **Успіх:** active package змінюється лише через чинний transactional engine.

### D07 — ZIP транзакція та артефакти

- **Початкові умови:** тестова транзакція стартувала.
- **Дії:** дочекайтеся успішного update; після нього перевірте `Server.next`,
  `Server.previous`, `Server.failed` і update-state journal згідно з результатом.
- **Очікувано:** package roles та журнал узгоджені; потрібні recovery артефакти
  не видаляються перед підтвердженим результатом.
- **Успіх:** операція відповідає стану журналу; нічого не «підчищалося» вручну.

### D08 — Автоматичний запуск служби

- **Початкові умови:** D06/D07 завершені.
- **Дії:** дочекайтеся перевірки SCM та API health у Manager.
- **Очікувано:** Service автоматично запускається з перевіреного active package.
- **Успіх:** SCM і API health обидва відповідають; сам Running не зараховується.

### D09 — API health і повідомлення результату

- **Початкові умови:** новий пакет встановлений; API перевіряється.
- **Дії:** прочитайте фінальний стан у Manager та повторіть безпечний API health
  запит.
- **Очікувано:** успіх показано лише для нового активного пакета після health.
- **Успіх:** UI повідомляє фактичний результат, без передчасного успіху після
  download або одного SCM Running.

### D10 — SQLite збережена

- **Початкові умови:** synthetic DB з контрольними тестовими записами та snapshot.
- **Дії:** виконайте успішний update і перевірте цілісність/контрольні записи
  штатними read-only засобами.
- **Очікувано:** ZIP update не замінює й не автоматично відкочує SQLite.
- **Успіх:** тестові записи й схема збережені; автоматичний SQLite rollback не
  заявляється.

### D11 — Конфігурація збережена

- **Початкові умови:** зафіксовані тестові Program/Data/Backup paths, bind/port і
  service config.
- **Дії:** після D09 перевірте ті самі значення та health.
- **Очікувано:** оновлення зберігає зовнішню конфігурацію й persistent data.
- **Успіх:** конфігурація збігається з базовим записом, API доступний.

### D12 — Recovery після server update помилки

- **Початкові умови:** окрема snapshot VM із synthetic DB; помилка/переривання
  відтворюється лише за підготовленим тестовим recovery сценарієм.
- **Дії:** скористайтеся чинними diagnostics/recovery діями; не видаляйте
  `Server.next`, `Server.previous`, `Server.failed` чи journal і не запускайте
  ручне копіювання.
- **Очікувано:** неоднозначність зупиняє автоматичні зміни та зберігає докази;
  recovery перевіряє SCM і API health.
- **Успіх:** результат відповідає recovery decision і підтвердженій готовності API;
  SQLite автоматично не відкочується.

## E. Негативні сценарії

E01–E10 виконувати на окремих snapshot VM і тільки з тестовими asset/data. Для
мережевих помилок бажано використовувати контрольований firewall/ізоляцію VM;
не редагуйте робочі release-файли.

### E01 — Відсутність інтернету

- **Початкові умови:** нова інсталяція без раніше підтвердженого update.
- **Дії:** вимкніть мережу VM і запустіть Client/Manager.
- **Очікувано:** асинхронна перевірка завершується зрозумілим станом; застосунок
  продовжує локальну роботу.
- **Успіх:** UI не завис, Service не зупинено автоматично.

### E02 — GitHub недоступний

- **Початкові умови:** контрольований DNS/firewall block до GitHub у VM.
- **Дії:** виконайте ручну перевірку та відновіть мережу.
- **Очікувано:** показана помилка мережі; до підтвердження релізу робота
  продовжується; підтверджений раніше gate не скидається.
- **Успіх:** після відновлення мережі перевірку можна повторити.

### E03 — Перерване завантаження

- **Початкові умови:** потрібен опублікований Stable asset; VM snapshot.
- **Дії:** перервіть мережу VM посеред download.
- **Очікувано:** partial файл не стає готовим пакетом; UI показує помилку й retry.
- **Успіх:** нова спроба після відновлення мережі завантажує/перевіряє повний файл.

### E04 — Пошкоджений пакет

- **Початкові умови:** від'єднана копія тестового пакета у disposable VM.
- **Дії:** змініть один байт у копії після download або використайте спеціально
  підготовлений тестовий asset з невірним digest.
- **Очікувано:** hash або embedded integrity validation відхиляє пакет до запуску
  NSIS/Service update.
- **Успіх:** пошкоджений пакет не встановлено, gate зберігається для retry.

### E05 — Недостатньо місця

- **Початкові умови:** окремий тестовий диск/VM із контрольовано малим вільним
  простором; не заповнюйте робочу машину.
- **Дії:** запустіть preflight або download/update.
- **Очікувано:** конкретна помилка місця до небезпечної заміни; поточний пакет
  і дані збережені.
- **Успіх:** після звільнення місця повтор проходить, recovery-файли не видалені.

### E06 — Відмова UAC

- **Початкові умови:** перевірений Client або Manager Setup готовий.
- **Дії:** відхиліть UAC prompt.
- **Очікувано:** нова версія не оголошується встановленою, обов'язковий gate лишається.
- **Успіх:** повторна спроба доступна, API Server не змінений.

### E07 — Перерване встановлення

- **Початкові умови:** snapshot VM; лише синтетичні дані.
- **Дії:** перервіть installer лише за окремим VM-сценарієм, де це безпечно;
  дочекайтеся процесу/launcher result, потім перевірте стан повторним запуском.
- **Очікувано:** відсутність підтвердження не показує update success; NSIS
  recovery-папки/marker обробляються чинним шляхом.
- **Успіх:** Manager/Client або відновлено, або gate лишився та retry/recovery
  доступні; не заявляється гарантований rollback Manager.

### E08 — Повтор після помилки

- **Початкові умови:** будь-який попередній update failure усунуто у snapshot VM.
- **Дії:** скористайтеся UI retry без ручного видалення transaction artifacts.
- **Очікувано:** послідовна повторна операція, без другого паралельного updater.
- **Успіх:** пакет перевірено знову й фактичний результат відображений.

### E09 — Некоректна версія і prerelease

- **Початкові умови:** синтетичні metadata у локальних automated tests; не
  публікуйте тестовий prerelease.
- **Дії:** запускайте чинні SemVer/Stable filtering tests; у VM використовуйте
  лише окремий контрольований тестовий GitHub Release після дозволу.
- **Очікувано:** некоректний SemVer, та сама/старіша версія та prerelease
  відхиляються.
- **Успіх:** локальний набір підтверджує фільтрацію; hosted behavior позначається
  окремо до виконання реального релізу.

### E10 — Незавершена серверна транзакція

- **Початкові умови:** synthetic Server/Data, snapshot VM і заздалегідь визначена
  recovery-стадія.
- **Дії:** відтворіть тільки дозволену тестову незавершену транзакцію; відкрийте
  recovery/diagnostics, нічого не видаляйте й не змінюйте SQLite вручну.
- **Очікувано:** автоматична операція блокується за неоднозначності; журнали та
  `Server.next`/`previous`/`failed` збережені.
- **Успіх:** чинний recovery визначає дію, потім окремо підтверджуються SCM та API
  health; небезпечного автоматичного SQLite rollback немає.
