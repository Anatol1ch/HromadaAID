# HromadaAID

HromadaAID — настільна клієнт-серверна система обліку матеріальних допомог для
органів місцевого самоврядування. Інтерфейс користувача українською мовою.

## Компоненти

| Компонент | Призначення |
| --- | --- |
| HromadaAID Client | Робота працівників із реєстрами та документами через API |
| HromadaAID API Server | Бізнес-операції, автентифікація, SQLite та серверні резервні копії |
| HromadaAID Server Manager | Локальне адміністрування встановленого сервера |
| Єдиний Windows Setup | Client-only, Server-only (API + Manager), Combined; Modify/Upgrade/Uninstall |

## Наявні можливості

- Облік отримувачів, банків, рішень і призначень матеріальної допомоги.
- Довідники, річне планування, звітність і формування платіжних відомостей.
- Формування Excel/PDF через Windows Excel COM та незмінені шаблони: персональні
  й зведені списки за видом допомоги та банком; банківські відомості лише за банком.
  У параметрах можна вибрати один, кілька або всі банки; таблиця має стовпець «Банк».
  Персональні списки діляться по 12 призначень; кількість означає призначення.
- Ручні адреси Loopback, LAN і Tailscale у Server Manager з локальним збереженням,
  редагуванням і копіюванням; автоматичне визначення адрес вилучено.
- Облікові записи, ролі й обмеження доступу до операцій.
- Вибіркове видалення призначень із перевіркою статусу та історії виплат.
- Підсумок реєстру за всіма записами поточного пошуку й фільтрів.
- Компактна навігація та гнучке компонування робочих сторінок.
- Обов'язкові адреси реєстрації та проживання з копіюванням у двох напрямках.
- Ручне налаштування й збереження адреси сервера в Client: HTTP з IPv4 або DNS-ім'ям
  на фіксованому порту 4310, через loopback, LAN або Tailscale. Повторне підключення
  використовує ту саму адресу; автоматичного пошуку й перемикання серверів немає.
- Первинне налаштування сервера, контроль служби/API, резервування,
  ZIP-оновлення та контрольоване recovery через Server Manager.
- Обов'язкові Stable GitHub оновлення Client/Manager через універсальний Setup
  та завантаження Server ZIP через чинний транзакційний updater.
- Перевірка оновлень Client доступна незалежно від входу та API Server; обов'язкове
  оновлення відображається поверх системних екранів.
- Після Client 1.1.1 updater узгоджує перехід між API Contract за цільовими
  маркерами release manifest і свіжою перевіркою сумісності сервера.
- Історія опублікованих стабільних Release Notes доступна з Client: вбудовані
  описи, GitHub Releases і кеш у профілі користувача.
- Налаштування Client відкриваються модальним вікном із категоріями «Загальні»,
  «Обліковий запис», «Підключення», «Оновлення» та «Про програму».

Client не має автономної робочої SQLite або адміністративного резервування.
Старі клієнтські backup-файли залишаються на диску й автоматично не мігруються.

Один API Server слухає IPv4 `0.0.0.0:4310` і працює з однією серверною SQLite.
Внутрішнього TLS немає; LAN HTTP не шифрує дані. Tailscale забезпечує тунель як
зовнішній інструмент: HromadaAID ним не керує й не налаштовує Windows Firewall.
Server Manager показує три вручну задані адреси лише на основному екрані.
Вони не змінюють listener, конфігурацію сервера чи адресу Client. Серверна конфігурація має єдиний формат v3 з полями
`programDirectory`, `databasePath`, `backupDirectory`; несумісний файл не мігрується
й не переписується автоматично. HTTPS зовнішніх сервісів збережено.

## Поточний стан

**Останній опублікований Stable — 1.1.0.** Цільовий Stable 1.1.1 готується;
його ще не публікували. API Contract залишається v2. Пакети й Release Notes
опублікованого випуску доступні на
[GitHub Releases](https://github.com/Anatol1ch/HromadaAID/releases/tag/v1.1.0).

Генерація документів не змінює фінансових даних. Сумісність формату
«ПриватБанк.xlsx» з імпортом інших банків не підтверджена. Ручні адреси Manager
зберігаються в профілі Windows-користувача та не підміняють перевірку доступності.

МФО перевіряється як 6 цифр, ЄДРПОУ — як 8 цифр; checksum ЄДРПОУ немає.
IBAN перевіряється добровільно кнопкою за українським форматом і MOD 97.
Успішна перевірка не підтверджує існування чи власника рахунка. Персональні
списки й надалі використовують адресу проживання та не підміняють її адресою
реєстрації.

Перехід із 1.0.2 вимагає оновити Server Manager → API Server → усі Client.
Порядок описаний в [інструкції оновлення](installation-and-administration.md).
Release Notes: [Stable 1.1.0](release-notes/1.1.0.md).

Для майбутньої зміни контракту Client відкладає міжконтрактне оновлення, доки
свіжа перевірка не підтвердить, що API Server підтримує цільовий контракт.
Якщо API недоступний, міжконтрактний перехід не підтверджується; сумісна поточна
версія Client може продовжити роботу. Оновлення в межах одного контракту
зберігає штатну політику. Ці правила доступні після встановлення Client 1.1.1;
вони не змінюють поведінку старих Client або ручного встановлення.

Технічні межі: [ARCHITECTURE](ARCHITECTURE.md), домовленості:
[DECISIONS](DECISIONS.md), статус етапів: [ROADMAP](ROADMAP.md).
